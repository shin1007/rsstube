# 無料枠と上限のまとめ

このアプリは全部を無料枠に収める前提で作ってある。どこが先に詰まるか、詰まったら
何をいじるかを1か所にまとめる。**実測値を正とする**（公開されている数字と食い違うことが
あるため。理由は最後に書く）。

最終更新: 2026-08-14

---

## 1. Gemini API（先に詰まるのはここ）

| 用途 | モデル | 1回で使う量 | 実測した上限 |
|---|---|---|---|
| 記事の要約 | `gemini-3.5-flash-lite` | 5記事で1回 | 未到達 |
| 台本の生成 | `gemini-3.5-flash` | 1本で1回 | **1日20リクエスト** |
| 音声の合成 | `gemini-3.1-flash-tts-preview` | セグメント1つで1回 | 未到達 |

### 台本の1日20回が実質の上限

2026-08-14 に `429 RESOURCE_EXHAUSTED` を受けたとき、エラー本文にこう出た:

```
Quota exceeded for metric: generativelanguage.googleapis.com/generate_content_free_tier_requests,
limit: 20, model: gemini-3.5-flash
```

**毎朝のダイジェスト1本なら1日1回**なので、通常の運用では当たらない。当たるのは
記事単位の深掘りを1日に何本も作ったときと、開発でプロンプトをいじって何度も試したとき。
実際、スキーマの調査で20回を使い切って、その日は台本を作れなくなった。

公開されている記事では Flash 系は500〜1500 RPD と書かれていることが多いが、
**手元のキーで返ってきたのは20**だった。モデルや時期で変わるので、
公開情報ではなく設定画面の使用量表を見ること。

### 使用量の見かた

設定画面に直近7日の呼び出し回数が出る（`ai_usage`・0009）。

- **失敗が並んでいたら上限に当たっている**。429 でジョブがバックオフし、要約や音声が
  静かに遅れる。落ちたようには見えないので、この表が唯一の手がかりになる。
- 失敗した呼び出しも1回ぶん枠を食うので `failures` として別に数えている。
- 日付の区切りは日本時間。Google 側のリセットは太平洋時間なので半日ほどずれる。

### 詰まったときにいじるところ

| いじるもの | 場所 | 効果 |
|---|---|---|
| 要約のまとめ数 | `BATCH_SIZE`（`lib/ai/summarize.ts`、既定5） | 増やすと呼び出し回数が減る。増やしすぎると出力が雑になる |
| 1回の実行で回す量 | `SUMMARIZE_BATCHES_PER_RUN` / `TTS_PER_RUN` / `SCRIPT_PER_RUN` | 1回あたりを減らすと、上限に一度に当たりにくい |
| ダイジェストの件数 | 設定画面「ダイジェスト件数」（既定8） | 台本の長さ＝TTS の回数に効く |
| 巡回の間隔 | `supabase/scheduler.sql` の `rsstube-poll` | 記事が減れば要約も減る |

有料キーに差し替えれば、コードはそのままで上限だけ上がる。

## 2. Supabase（無料プラン）

| 資源 | 上限 | いまの使い方 | 効いている対策 |
|---|---|---|---|
| Postgres | 500MB | 記事本文がほぼ全部を占める（本文平均8KB） | `purge_article_bodies()` が保持期間（既定90日）を過ぎた既読記事の本文を消す |
| Storage | 1GB | 生成した音声。**MP3で473KB/分**（10分4.6MB） | `/api/cron/purge` が `media_retention_days`（既定30日）を過ぎたものを消す |
| 自動バックアップ | **無し** | — | `npm run db:backup` を手で回す（PITR も無い） |

### 音声の容量が効く

TTS が返すのは生PCM（24kHz モノラル）で**1秒48KB**。そのまま置くと8分で23MBあり、
1GB は40本ほどで埋まる。64kbps の MP3 にして約6分の1にしてある（実測473KB/分、
1GB に約220本）。毎朝1本なら半年以上もつが、記事単位の深掘りを増やすと一気に縮む。

**行を消しても Storage のファイルは残る。** 容量の実体はファイルのほうなので、
音声の掃除だけ SQL ではなくルート（`/api/cron/purge`）に置いてある。

## 3. Vercel（Hobby プラン）

| 制約 | 影響 | 対策 |
|---|---|---|
| Cron は**1日1回**まで | 1時間毎の巡回ができない | 定期実行は全部 Supabase の `pg_cron` に寄せた（`supabase/scheduler.sql`） |
| Cron の実行時刻が**±59分ずれる** | 6時のダイジェストが7時前にできる | 同上。時刻の判定はアプリ側で持つ |
| 関数の実行時間 **60秒** | TTS は1セグメントに数十秒かかる | ワーカーは `TIME_BUDGET_MS`（45秒）を見ながら切り上げる |

**60秒を超えると関数ごと落とされ、`running` のままのジョブが宙に浮く**
（`reclaim_jobs()` が拾い直すまで止まる）。件数だけで絞っても1件あたりの時間は
相手次第なので、時間で切るほうを主にしている。

---

## 4. その他

- **Web Push**: 送信側の上限は無い。使えなくなった購読先は 404/410 が返った時点で消す。
- **フィードの取得**: 相手のサーバー次第。ETag / Last-Modified の条件付きGETで、
  更新が無ければ 304 で即終わる。連続失敗したフィードは `error_count` 時間ぶん
  間隔を空ける（10回失敗すれば10時間に1回まで落ちる）。

## 5. 詰まりの見分けかた

| 症状 | 疑うところ | 確かめかた |
|---|---|---|
| 要約が付かない記事が増える | Gemini の RPD | 設定画面の使用量表。`failures` が並んでいるか |
| 音声が「合成中」から進まない | Gemini TTS の RPD、または60秒切れ | 同上＋`jobs` の `last_error` |
| 音声が作れなくなった | Storage 1GB | Supabase のダッシュボード |
| 記事の取得が止まった | pg_cron が動いていない | `select * from cron.job_run_details order by start_time desc limit 20;` |
| 特定のフィードだけ古い | そのフィードの連続失敗 | 設定画面のフィード一覧に失敗回数と理由が出る |

---

## 6. なぜ実測を正とするか

公開されている無料枠の数字は、モデル・時期・キーの素性で変わる。実際、
`gemini-3.5-flash` は多くの記事で500〜1500 RPD と書かれているが、手元のキーで
返ってきたのは20だった。**アプリ自身に使用量を記録させてあるのは、
外の情報ではなく自分の枠を見るため**（`ai_usage`・0009）。

数字を疑うときは、設定画面の表と、429 のエラー本文（`limit:` が書かれている）を見ること。
