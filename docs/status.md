## 10周目 — 長い記事は続きから開きます（9/7・本番に出ています）

**議事録のような長い記事を、開き直したときに前回の位置から読めます。**

実データで最長は 40,000字（審議会の議事録）で、500字/分なら80分ぶん。通勤で読む
ものなので途中で降りますし圏外にも入りますが、それまでは開き直すたびに先頭からで、
**どこまで読んだかを目で探し直す**ことになっていました。

- **黙って途中から出しません。** 「前回の続きから開きました／先頭へ」を5秒だけ出します
  ——先頭にあるはずのものが無いと、まず「壊れた」と思うので
- **読み切ったものは覚えません**（9割まで来ていたら忘れる）。末尾へ飛ばされると
  「戻れない」ようにしか感じられないので
- 覚えるのは**この端末だけ**（localStorage）。スマホで読みかけたものをPCで続ける、は
  この使い方ではまず起きないので、サーバーには持たせていません

本番の iPhone 相当で、2500px まで読む → 一覧へ戻る → 開き直すと 2500px から出る、
まで確認済みです。

## 9周目 — 地下鉄でも読めます（9/7・本番に出ています）

**通勤前にアプリを開いておけば、圏外でも未読20件を読めます。**

これまでサービスワーカーは意図的に何もキャッシュしておらず、電波が無いところで
開くと「オフラインです」の1枚が出るだけでした。**朝の通勤前に開くのが主な使い方**
だと決めてあるのに、そこが穴になっていました（`docs/usability.md` の3）。

- アプリを開いて**4秒たってから**、未読20件を本文つきで静かに落とします
  （1時間に1回まで。巡回が1時間毎なので、それより短くしても新しいものは増えません）
- **画像は持ち出しません。** 圏外では取れないので、置いても壊れた枠が並ぶだけです。
  そのぶん軽くなります（本番の実測で **20件・314KB**）
- 圏外で開くと、記事の一覧と本文がそのまま読めます。「いつ時点のものか」も出ます
- **既読は付きません。** 圏外では書けないので、まず「読めるだけ」で切りました
  （画面にもそう書いてあります）。電波のあるところで開き直すと本体に戻ります
- 「データ通信の節約」を出している端末では落としません

本番のブラウザで、オンラインで開く → 圏外にする → 一覧20件が出る → 記事を開いて
本文が読める → 一覧へ戻る → オンラインに戻すと本体へ帰る、まで確認済みです。

**実機で見てほしいところ**: アプリを開いて少し待ってから**機内モードにして開き直す**と、
「圏外です」の下に記事が並ぶこと。並ばない場合は、機内モードにする前に1分ほど
開いたままにしてから試してください。

## 8周目 — 押してから出るまでが 85ms 短くなりました（9/7・本番に出ています）

**画面遷移に必ず乗っていた 124ms のうち約80msは、Vercel が proxy（middleware）を
1回起こす費用でした。** 中身ではなく器の費用だと確かめたうえで、器ごと外しました。

本番の実測（中央値）。**TTFB＝押してから最初の1バイトが返るまで**:

| 押したとき | 前 | 後 |
|---|---:|---:|
| 一覧「未読」 | 249ms（TTFB 141） | 236ms（TTFB **57**） |
| 一覧「すべて」 | 352ms（136） | 261ms（**53**） |
| フィードで絞る | 240ms（138） | **143ms**（43） |
| 記事を開く | 317ms（133） | 248ms（**44**） |
| 聴く | 236ms（129） | **152ms**（44） |
| 書き出し | 246ms（131） | **154ms**（40） |
| アーカイブ | 312ms（130） | 235ms（**50**） |

**ホーム画面から起動したときに CSS と JS を落とし始められる時刻**（`</head>` の到着）は
**471ms →（9/7 未明）142ms → 56ms** になりました。2日前の8分の1です。

### 認証はどこへ行ったか

proxy がやっていたのは「未ログインを弾く」と「セッションの更新」の2つで、
それぞれ移しました。

- **弾くのは各ページの入口**（`lib/auth/guard.ts`）。見るのは Cookie の期限だけで、
  署名の照合はしません——**読み書きの可否は今までどおり Supabase 側の RLS が
  決める**ので、Cookie を書き換えても枠が出るだけで中身は1行も取れません
- **更新は `/auth/refresh`**。アクセストークンは1時間で切れるので、**朝いちばんの
  1回だけ**ここを通ります（更新して、開こうとしていた URL へ戻します。記事の
  URL をそのまま開いても、その記事に戻ります）。使っている間は、スター・あとで・
  既読などの操作が Cookie を書けるので自然に更新されます

**通した経路（本番で確認済み）**:

| | 結果 |
|---|---|
| ログイン済みで `/` `/settings` | 200 |
| ログイン済みで `/login` | 一覧へ戻す |
| 未ログインで `/` `/listen` | ログイン画面へ |
| 壊れた Cookie | ログイン画面へ |
| 期限切れで記事の URL を開く | 更新して、その URL へ戻る |
| 更新しても直らないとき | ログイン画面へ（往復し続けない） |
| `/api/opml` Cookie 無し / 有り | 401 / 200 |
| `/api/cron/poll` 秘密無し | 401 |
| `/manifest.webmanifest` `/sw.js` `/offline.html` | 未ログインでも 200 |

本番の iPhone 相当（WebKit）でも、期限切れの状態から開いて一覧が出るところ、
5画面を回るところ、記事を開いてスターが DB に入るところまで確認しています。

**もし朝いちばんにログイン画面が出たら**、それは更新トークンまで切れていた
（1〜2週間触っていない）ときです。パスキーかパスワードで入り直してください。
そうなっていないかは、この後もこちらで見ています。

## 7周目 — 夜のあいだにやったこと（9/7・本番に出ています）

### 速さ

**朝いちばんの回線で、触ってもいない記事を半メガ落としていました。**
本番のスマホ幅で数えたところ、一覧を開くと先読みが11本飛び、うち2本が
**記事のページ丸ごと**（実測 140.9KB と、長い議事録で 370KB）。出どころは
2つとも「押しそうだ」の読み違いでした:

- キーボードのカーソルは何もしなくても先頭に居るので、**開いた瞬間に先頭記事**を
  取りに行っていた（スマホでは j/k を使わないので、ほぼ確実に無駄になる）
- 本文ペインはスマホでは畳まれているだけで DOM には居るので、**一覧を見ている
  だけで「次の記事」**を取りに行っていた

人がカーソルを動かしてから／ペインが実際に見えているときだけ取りに行くように
しました。本番の iPhone 相当で **記事の先読み 2本 → 0本**。`j` を押せば今までどおり
取りに行くので、キーボードで読む速さは落ちていません。PC は変えていません。

**先頭記事の本文を待たずに一覧を出すようにしました。** 「何も選んでいないときは
先頭を出す」ぶんの本文は、一覧が返ってこないと行き先が決まらないので、
**一列に足される往復**でした。スマホでは畳まれていて見えないのに毎回払っていた
ぶんです。手元の本番ビルドで一覧の到着が 268ms → **208ms**（本文の到着は変わらず）。

**設定の「進み具合と使用量」を後ろに回しました。** `pipeline_status()` はこの画面で
いちばん遅い問い合わせ（他が往復の下限＋5〜15ms に対して＋70ms）なのに、
フィードの追加や朝の時刻と一緒に待っていました。設定の本体 285ms → **190ms**。

### 読みやすさ

- **記事のメニュー（☰）が本文に被っていたのをやめました。** 本文の上に浮かせて
  いたので、読んでいる行の右端 48px が常に隠れていました。下の帯
  （前の記事 / 次の記事）の中に入れてあります。指の届く場所は同じです
- **記事の1行目**（情報源 / 著者 / 日付 · N分 · 取得）を2行に分けました。情報源の
  名前は長いものが多く、スマホでは必ず折り返して日付が行の途中に散っていました。
  **情報源を押すと、その情報源の記事だけの一覧へ移ります**
- **一覧に「いま何の中を見ているか」を出しました。** 絞り込み中は名前が名札で出て、
  押せば外せます。0件のときの文面にも名前が入り（「◯◯ に未読はありません」）、
  広げる先のボタンが1つ出ます（「◯◯ のすべてを見る」「絞り込みを外して探す」）
- 一覧の行のメタが折り返して行の高さが揃わなかったのを直しました

### 分かったが、やらなかったこと

**画面遷移に必ず乗る 124ms のうち約80msは、Vercel が proxy（middleware）を
1回起こす費用です。** 手元で同じ proxy を通しても静的ファイルと差が出ない
（15.5ms 対 16.2ms）ので、こちらのコードは無料で、**80ms は器のほう**だと
確かめました。消すには認証をアプリ側へ移す（Server Component で検証し、
期限切れだけ Route Handler で更新する）ことになりますが、**失敗すると朝いちばんに
ログインし直しになる**ので、寝ているあいだに入れるものではないと判断しました。
入れるかどうかはご判断ください（毎回の遷移が 250〜350ms → 170〜270ms 相当）。

**JS の量は手がありません。** 一覧で落ちる 559KB のうち 380KB は React と Next の
本体で、こちらのコードは 119KB です。

## 6周目 — 残りの画面も枠から先に出ます（9/7・本番に出ています）

5周目で `/` に入れたものを、二次画面にも入れました。**どのページも、中身を
待たずに枠が出ます。** 本番（東京）の実測——「CSS と JS を落とし始められる
時刻」（＝ `</head>` が届いた時刻）:

| | 前 | 後 |
|---|---:|---:|
| `/`（読む） | 471ms | **161ms** |
| `/library`（アーカイブ） | 375ms | **161ms** |
| `/settings`（設定） | 376ms | **177ms** |
| `/exports`（書き出し） | 257ms | **151ms** |
| `/listen`（聴く） | 256ms | **144ms** |

**どれも 150ms 前後に揃っています。** これは Vercel が関数を1回起こす費用
（124ms）とほぼ同じで、**ここから先はこちらでは動かせない**ところです。
中身が届く時刻（`/settings` 351ms など）は変わっていません——変わったのは
「待っているあいだにブラウザが働けるかどうか」です。

## 押したときに反応が出ます（9/7）

**画面遷移だけ、押しても何も起きない時間がありました。** スター・あとで・
書き出しはどれも押した瞬間に見た目が変わるのに、タブやフィードを押したときは
250〜380ms のあいだ画面が押す前のまま。これは React の遷移の正しい動き
（新しい中身が揃うまで今の画面を出したままにする）なのですが、押せたのか
どうかが分かりませんでした。

**画面のいちばん上に細い帯**を出すようにしました。骨組みに差し替えるのは
やめています——いま読んでいるものが消えるほうが、待たされるより悪いので。
進み具合は出しません（本当のところが分からないので、出せば嘘になります）。
先読みが間に合ったときは何も出ません（速いのに遅く見えるのを避けるため）。

本番を WebKit（iPhone 13 の見立て）で5画面ぶん開いて確認済みです。
コンソールに出るのは、そのブラウザがサービスワーカーに対応していないぶんの
1件だけ（`/sw.js` 自体は 200 で配信されています）。

**実機で見てほしいところ**: ホーム画面から起動した直後に**灰色の枠**が出るか、
下部タブを押した直後に**上端に細い青い帯**が出るか。

## 5周目 — 起動の待ちを詰めました（9/7・本番に出ています）

**ホーム画面から開いたとき、画面に何か出るまでが 330ms 早くなりました。**

遅かったのはサーバーではありません。`/` はページ全体が1つの関数で、**DBの
問い合わせが全部終わるまで `<head>` を1バイトも出していませんでした**。
ブラウザは `<head>` が来るまで CSS（45KB）も JS も落とし始められないので、
「サーバーを待つ」と「ファイルを落とす」が一列に並んでいた形です。
サービスワーカーの先読みも静的ファイルのキャッシュも、**URL が分かってから
しか働けない**のでここは効いていませんでした。

本番（東京）の実測——応答を届いた順に時刻付きで読んだもの:

| `/` を開いたとき | 前 | 後 |
|---|---:|---:|
| CSS/JS の在りかが届く（＝落とし始められる） | 471ms | **142ms** |
| 記事の中身まで全部届く | 473ms | 248ms |

**変えていないページが動いていないことが、上の差が本物だという証拠です**
（`/listen` 256ms・`/exports` 257ms・`/settings` 376ms は、いまも
「最後の1バイトと `<head>` が同時」のまま）。

待っているあいだは、記事一覧の**枠だけ**が灰色の帯で出ます。数字も記事名も
下部タブの文字も出していません——押せない文字が出ていると、反応しないアプリに
見えるためです。

**画面の中の移動（タブを押す等）の見え方は変わりません。** 骨組みが挟まるのは
最初の1枚だけで、遷移では今の画面を出したまま待ちます（本番の iPhone 相当の
ブラウザで、押した前後に骨組みが出た回数を数えて 0 回）。

本番を WebKit（iPhone 13 の見立て）で開いて確認済み。コンソールのエラーは
ありません。測り直す口は `node --env-file=.env.local scripts/head-probe.mjs`。

**まだ残っているもの**: 起動のいちばん重い部分は、そのあとに落ちてくる JS
（全部で 816KB・圧縮前）です。2回目からはサービスワーカーが手元に持っている
ので効きませんが、**アプリを更新した直後の初回**はここが効きます。
`/library` `/listen` `/exports` `/settings` は今回の直しを入れていないので、
通知から `/exports` を開くような入りかたでは前のままです。

## 4周目 — 一覧が軽くなりました（9/6・本番に出ています）

**押してから一覧が出るまでが 60〜90ms 短くなりました。**「あと何件」を数える
問い合わせを、一覧を取るのと**同じ1回**にまとめたぶんです。並べて投げてはいたの
ですが、並べたところで待つのはいちばん遅い1本で、**そのいちばん遅い1本がこれ**
でした（一覧79ms に対して件数だけで112ms）。同じ問い合わせに載せても時間は
増えません。

本番の実測（中央値・運ぶ量が同じものだけ並べています）:

| 画面 | 前 | 後 | |
|---|---:|---:|---|
| 一覧「あとで」 | 342ms | **252ms** | −90ms |
| フィードで絞る | 336ms | **247ms** | −89ms |
| 一覧「すべて」 | 431ms | **361ms** | −70ms |
| 検索 | 348ms | **286ms** | −62ms |
| 一覧「未読」 | 334ms | **270ms** | −64ms |

変わらないはずの画面（聴く・書き出し・設定・アーカイブ）は動いていません
（20ms 以内）。**そこが動いていないことが、上の差が本物だという証拠**です。

**指の下も軽くなりました。** 一覧の行を1行ずつ「変わっていなければ描き直さない」
形にしました。それまでは、引っぱって更新している最中・帯が出たとき・
カーソルを1つ動かすたびに、**画面にある行が全部描き直し**になっていました。
手元の本番ビルドで j/k を80回叩いた実測（1回あたり）:

| 一覧の行数 | 前 | 後 |
|---|---:|---:|
| 60行（1ページ目） | 中央値 32ms・最悪 222ms | **16.7ms**（＝1フレーム。これ以上は速くならない） |
| 240行（下まで3回継ぎ足した状態） | 中央値 111ms・最悪 662ms | **16.6ms** |

**スマホで効きます。** 引っぱって更新は指を動かすたびに描き直しが走るところで、
下まで読み進めているほど重くなっていました。

本番のブラウザで、一覧・検索（27件）・「要約なし」（37件）・無限スクロール
（60→120→180→240件）まで動かして確認済みです。コンソールのエラーはありません。

**手元での確認が、共有している本番のデータに触れています。** 記事を4〜5本
開いたので、そのぶんは既読になりました（DBは手元も本番も同じもの）。

## 画面遷移の速さ（9/6）

本番（東京・hnd1）で全ページを実測してから直しました。数字は**中央値**で、
`node --env-file=.env.local scripts/perf-probe.mjs` を叩けばいつでも取り直せます
（パスワードは要りません）。**run ごとに ±30ms は動く**ので、30ms 未満の差は
誤差として読んでください。

RSC（＝画面のリンクを押したときに実際に飛ぶもの）:

| 画面 | 前 | 後 | |
|---|---:|---:|---|
| 設定 | 441ms | **316ms** | −125ms |
| 再生（/watch） | 350ms | **237ms** | −113ms |
| 一覧「すべて」 | 411ms | **340ms** | −71ms |
| 検索 | 387ms | **352ms** | −35ms |
| アーカイブ | 366ms | **336ms** | −30ms |
| 聴く | 274ms | **247ms** | −27ms |
| 一覧「未読」 | 280ms | 276ms | 誤差 |
| 記事を開く | 321ms | 331ms | 誤差 |

最初の1枚（HTML）: 設定 463→**347ms**、アーカイブ 457→**359ms**、
書き出し 329→**268ms**、一覧 374→**343ms**。

**スター・あとで・既読も速くなっています。** 押すたびに Server Action を1本
呼ぶのですが、そこに「ログインしているか」を Supabase に聞きに行く往復
（約134ms）が乗っていました。proxy でやめたはずの往復が、押す側には

**残っている待ち時間の内訳**（一覧を押したとき 276ms のうち）:

  （Cookie を1本も送らなくても111msかかるので、認証の中身ではありません）
- 残り約156msがページを組んで流すぶんです

### 3周目 — Cache Components（入れて、戻しました）

**入れたものは戻してあります。** 押した瞬間にサイドバーが出るところまでは
行ったのですが（本番のブラウザで実測12〜26ms）、**実機の iPhone で
 「画面を出せませんでした」**が出たためです。こちらでは再現できませんでした
 ——サーバーが返す HTML は正常、curl も 200、Chromium はスマホ幅でも通ります。
手元に iPhone と同じブラウザ（WebKit）が入っていないのが、確かめきれなかった
いちばんの理由です。毎朝読むものなので、原因の分からないまま置かないことにしました。

**時刻が9時間ずれていたのを直したぶんは残してあります。** これは Cache Components
とは関係のない実害で、サーバー側で日時を文字にするとき時間帯を渡しておらず、
**本番（Vercel は UTC）だけ**ずれていました——「取得 12:07」が実際には「3:07」
だった、という形です。手元は日本時間なので気づけませんでした。

速さは1周目・2周目のぶん（下の表）が効いたまま残っています。

### 2周目（同じ日）

| | 前 | 後 | |
|---|---:|---:|---|
| 検索（RSC） | 352ms | **290ms** | −62ms |
| 一覧「未読」の最初の1枚 | 343ms | **282ms** | −61ms |
| アーカイブの最初の1枚 | 359ms | **316ms** | −43ms |
| アーカイブ（RSC） | 336ms | **304ms** | −32ms |

- **検索**は `ilike` をやめて PGroonga の `&@` にしました。索引は前から効いて
  いて、遅かったのはそのあと**本文1199件を読み直して照合する**ぶんです。
  **当たる件数は減りません**——11語で突き合わせて9語は同数、2語は

## 8/26 に直したこと — 音声化が詰んでいた

**音声1本が `synthesizing`（合成中）のまま8日間止まっていました。**
5セグメント中4つまでできていて、最後の1つが Gemini の無料枠切れ（429）で
5回試して諦めた状態です。

壊れ方は「静かに壊れる」型でした。

| どこが | どうなっていたか |
|---|---|
| ワーカー | ジョブが諦めても、`media` の行を誰も `failed` に落とさなかった |
| 「聴く」 | ready でも failed でもない行を「生成中」とみなすので、**できあがり予定時刻を永久に出し続けていた** |
| 再生画面 | 同じ理由で「生成中」。失敗だと分かる場所がどこにも無かった |
| 「音声にする」 | 一意索引に当たるので、押し直しても「既に作ってあります」しか返らず**二度と作れない** |

直したもの（`0027_media_recovery.sql` と、それを呼ぶ側）:

- **見捨てられた音声を落とす** — 生きたジョブ（順番待ち・実行中）が1つも無くなった
  ものだけを `failed` にします。ワーカーが毎回、時間予算の外で必ず通ります。
  「何分経ったら」で判定しないのは、再試行のバックオフ（最大12時間）と食い違って
  まだ生きているものを殺すため
- **作り直せるようにした** — 「聴く」と再生画面に「↻ 作り直す」を出しました。
  **できているところは作り直しません。**上の1本なら、残り1セグメントだけをやり直します
  （台本づくりは1日20回しか叩けないので、全部やり直すと詰まった原因の枠切れを
  もう一度踏むことになる）
- **詰まっていた1本は 8/27 に直りました。**オーナーが「↻ 作り直す」を押し、
  残り1セグメントだけをやり直して完成しています

### パスキーでログインできるようにしました（`0034`）

- 指紋・顔・端末のPINで入れます。**パスワードは残します**——端末を替えたときや
  生体認証が通らないときに戻る先が要るためです。
- **登録は設定画面**（「パスキー」の欄）から。ログイン中にしかできません。
  ログイン画面には「パスキーでログイン」のボタンが出ます（対応していない
  ブラウザでは何も出しません）。
- **メールアドレスは打たせません。** 端末に「このサイトの鍵」を持たせる形
  （residentKey）で登録するので、選ぶだけで入れます。打たせたうえで
  「そのアドレスに鍵があるか」を返すと、アドレスの当たり判定にも使われます。
- **Supabase の Auth に WebAuthn はありません**（2026-08 時点）。署名の検証は
  こちら（`@simplewebauthn/server`）で行い、通ったら Secret キーで
  マジックリンクを1本作って、その token_hash を自分で `verifyOtp` します
  （`lib/auth/passkey-session.ts`）。**メールは飛びません。**
- **鍵はドメインに紐づきます。** 本番で登録したパスキーは、プレビュー用の
  ドメインや `localhost` では使えません。仕様なので、こちらでは直せません。
- 許可アドレス（`ALLOWED_EMAILS`）の確認は、鍵が正しくても通します——
  パスワードの入口と同じ壁を立てています。

## RSS の無いページ — 実測（8/26）と方針（8/27）

`回復術士のやり直し` のように、**サイトがRSSをやめてしまった**ページがある。
「更新があったことが分かればいい」という要望に対して、10ページで実測した。
（この節は owner-todo.md から移した。指示ではなく調べた結果なので、こちらが置き場所。）

- **本文テキストのハッシュを比べる方法は使える。** 10ページ中10ページでハッシュが
  安定し（3秒あけて2回取って変化なし）、8ページで「フィードの最新記事の題」が
  ページ本文に出ていた＝更新で必ず変わる
- **生HTMLのハッシュは使えない。** 4ページ中2ページが3秒で変わった（広告枠）
- **登録するURLの選定がすべて。** ComicWalker は素のURLだと「第1話」が出たままで
  **新話が出ても変わらない**。`?episodeType=latest` を付けると最新話が出る
- **どのURLが良いかを自動で判定する方法は見つからなかった。**
  「最近の日付が本文にあるか」で判定を書いたら11件中3件を間違え、しかも
  「絶対に鳴らないURL」を合格と判定した

**方針（8/27、オーナーの判断）**: 作る。**更新があったことだけを知らせる。**
中身は取りに行かない（RSS が無いページから本文を組み立てようとすると、広告や目次を
本文として掴んで、要約まで巻き添えになる）。出しかたは**普通の記事と同じ形**にして、
一覧に1行増やす——「RSS が無いので中身は取れていません」と記事の中身として書く。
専用の画面も通知の種類も増やさないので、スター・あとで・既読がそのまま使える。

**まだ実装していない。**まず ComicWalker の `?episodeType=latest` 1本で試す
（次の更新は9月上旬の見込み）。

## 8/27 に直したこと — 日付と要約

### 千葉県の103件に日付が入っていなかった

フィードが `<pubDate>Wed, 26 Aug 2026 17:00:00 JST</pubDate>` と書いてきますが、
**`JST` は JavaScript が解釈できません**（RFC 822 が名前で認めているのは
UT / GMT と北米の4つだけ）。取り込みも本文も要約も正常に通り、日付だけが
欠けていました。一覧は日付なしを末尾に置くので、**103件（全体の29%）が
リストの一番下に沈んでいました**。「新着なのに出てこない」としか見えません。

- `lib/feeds/date.ts` で名前のタイムゾーンを読み替えます（JST / JDT / KST のみ。
  `CST` や `IST` は国によって違う時刻を指すので入れません）
- **既存の行も勝手に埋まります**（`0030`）。取り込みのついでに、その回の取得に
  入っていた項目ぶんだけ日付を入れ直します。手で直す作業は要りません
- **実際に埋まったことを確認済み**: 日付なし103件 → **0件**

### 先回りできないので、欠けたら見えるようにしました

タイムゾーンの略号を全部先に登録することはできません（`MSK` `CEST` …）。
健康診断が「日付が無い」フィードを出すようにしたので、次に知らない略号の
フィードを登録しても設定画面に出ます。

### 要約が「本文が取得できない」で埋まっていた

タイトルしか無い記事に要約を頼むと、モデルは*入力の説明*を返してきます。
一覧にそれが並び、無料枠も1件ぶん使います。

プロンプトで禁じるだけでは足りませんでした（24件→5件までしか減らない）。
**素材が空なら呼ばない**のが正解で、積む側と渡す側の両方で弾くようにしました。
購読中のフィードでは**0件**になっています。
