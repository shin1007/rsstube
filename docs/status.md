## Supabase の「Critical」を塞ぎました（9/9）

ダッシュボードの警告（`rls_disabled_in_public`）が指していたのは
**`schema_migrations`** です。**記事・要約・購読は無事**でした——18表すべて RLS 済みで、
この1つだけが漏れていました。

見つけにくかったのは、**この表だけが `supabase/migrations/` ではなく
`scripts/db-migrate.mjs` の `create table if not exists` で作られていた**からです。
移行を管理する側の道具なので 0001 に書けず、そのぶん「表を作ったら RLS」の手順から
外れていました。migrations を見比べるだけでは全表 RLS 済みに見えます。
**本番に何があるかは本番の `pg_class` に聞いて**確定させました。

`public` に置いた表には Supabase が anon / authenticated へ既定で全権限
（SELECT / INSERT / UPDATE / DELETE / TRUNCATE）を渡します。RLS が無いので、
**ブラウザに出ている anon キーだけで誰でも読み書き・削除できる**状態でした。
実害は流出よりも移行の記録のほうで、行を消されれば次の `db:migrate` が 0001 から
流し直そうとして落ち、偽の version を入れられれば以後の移行が黙って飛びます。

`0044` で RLS を有効にし（ポリシーは置きません。所有者の postgres は迂回するので
`db:migrate` はそのまま動きます）、**`revoke all ... from anon, authenticated` まで**
やりました。権限を残したまま RLS だけ有効にすると「0行が返る」形で通ってしまい、
権限を取り上げてあれば手前の 401 で止まります。

| | 前 | 後 |
|---|---|---|
| RLS 有効な表 | 19中18 | **19中19** |
| anon の権限 | 全部 | **なし** |
| anon キーで `/rest/v1/schema_migrations` | 行が返る | **401 `42501`** |

本番に適用済みです（#164）。**Advisor の表示は再スキャンするまで残る**ので、
そこだけ owner-todo の「2」に置きました。

## 21周目 — 正体は「接続の張り直し」でした（9/8）

「うちDB」の列で **1218〜1590ms** と出たので、DB そのものを疑う前に、
手元から Supabase の REST を**間隔だけ変えて**叩きました。

| 前の1回からの間隔 | 1本の時間 |
|---|---:|
| 続けて | 17ms |
| 5秒 | 74ms |
| 10秒 | 96ms |
| 30秒 | 245ms |
| 60秒 | **559ms** |

**DB は遅くありません。** 空いた時間ぶん接続が切られていて、毎回 TCP と TLS を
張り直していました（Supabase の REST は Cloudflare の後ろにいます）。
Node の既定の keep-alive は **4秒**なので、少し間が空けば必ずこうなります。
**ホーム画面から開く1回は、いつでもその張り直しに当たります。**

接続を保つ形で同じ試験をすると、30秒あけても **29ms** でした。

### 直したこと

`lib/supabase/fetch.ts` が、接続を5分保つ fetch を supabase-js に渡します
（`server.ts` と `admin.ts` の両方）。**Node の global fetch は触っていません**
——フィードの取得は相手が何百とあるので、そちらまで接続を持ち続けたくないためです。

本番で、**こちらからは何も叩かず pg_cron の温めだけが走った状態で1本投げる**
（＝ホーム画面から開く1回と同じ形）を、前後で4回ずつ測りました:

| 状態 | うち DB | 平均 |
|---|---|---:|
| 接続を保つ前 | 610 / 826 / 618 / 808ms | 715ms |
| 保ったあと（1回目） | 504 / 341 / 597 / 327ms | **442ms** |
| 保ったあと（2回目・同じ設定） | 873 / 677 / 292 / 766 / 585ms | **639ms** |

**最初は「4割減りました」と書きましたが、訂正します。** 同じ設定で測り直すと
442ms と 639ms が出る幅があり、**4〜5回では差を言えません**。接続を保つこと
自体は効いています（間隔を変えた試験は 17ms 対 559ms とはっきり出ます）が、
**画面の待ち時間としては、インスタンスの当たり外れのほうが大きい**というのが
正しい読み方でした。

### この件で、効かずに戻したもの（2件）

- **`/rest/v1/` を素の fetch で叩くだけの温め**（#156 → #157）。1本目と2本目の
  開きが 322ms → 301ms で誤差。接続を開けても**すぐ切れていた**ので効きませんでした
- **1インスタンスに1回だけの温め**（#159）。同じ理由。いまは45秒に1回に変え、
  接続を保つ側とセットで効いています

### いまの見込み

実機の数字は、この2つが乗ります:

- 本文ペインをスマホに組まなくなったぶん（**273ms と 8KB**、20周目）
- DB を待つぶんが 4割減（**平均 715ms → 442ms**）

前回の実機が「完了 1591〜2234ms」でしたので、そこから 500ms 前後は縮んでいるはずです。
**確かめたいので、気が向いたときに1回だけ設定の表を送ってください**（急ぎません）。

## 20周目 — 「一覧」の列で決着しました。遅いのはサーバーです（9/8）

4件目の記録（21:51）で、犯人の位置が決まりました。

    接続 9ms → 応答 279ms → 一覧 1814ms → 受け終わり 2087ms → 描画 2196ms

**`<head>` は 279ms で届いています。** そこから**一覧が届くまで 1.5秒**。
つまり「届いていたのに描かれない」ではなく、**サーバーが組んでいる途中**でした。
手元から同じ `/` を叩くと骨組み 60ms・一覧 160ms なので、**手元では絶対に
見えない差**です（何度も叩くので、いつも温まっている側しか測れません）。

もう1つ分かったのは、**描画が毎回「受け終わり」の 110ms 後にしか来ない**こと。
4件とも同じです。`<Suspense>` で骨組みを先に流す設計は、**この端末では画面に
効いていません**（Chromium では描画 208ms・受け終わり 300ms と逆順になります）。
効いていない以上、詰めるべきは合計の時間です。

### 直したこと — 見えないペインを、スマホには組まない

本文ペインは `hidden md:flex` で**スマホでは見えていない**のに、記事を1本
まるごと取ってきて流していました。実機の記録でその代金が出ています:

| | スマホ |
|---|---|
| 一覧 1814ms → 受け終わり 2087ms | **273ms** |
| HTML | **9KB と 17KB**（展開後 54KB と 90KB） |

サーバーには画面の幅が分からないので、`layout` の `<head>` の script が
`rsstube-w=w|n` を置き（境目は `md` と同じ 768px）、`page.tsx` が読みます。
**UA では振り分けません**——タブレットの三ペインと細い窓のデスクトップが崩れます。
手元で確認した結果:

| | Cookie | HTML | 本文ブロック |
|---|---|---|---|
| スマホ(375) | `n` | **50KB** | 0 |
| PC(1280) | `w` | 78KB | 1 |

記事をタップしたときは今までどおり本文が出ます（確認済み）。幅を変えた直後の
1枚だけ Cookie が前の幅のままなので、そのときは空にせず「記事を選ぶと本文が
出ます」と出します（次の遷移で戻ります）。

### 残り 1.5秒の内訳を、あと一段割ります

「DB を待っているぶん」なのか「そのインスタンスで初めてページを組むぶん」なのかは、
まだ分かれていません。**`Promise.all`（サイドバー＋一覧）にかかった時間を
そのまま HTML に埋めて端末へ渡す**ようにしました。表に「うちDB」の列が増えています。

- **うちDB が 1.4秒** → DB 側。問い合わせか接続を直します
- **うちDB が 200ms** → 初めて組むぶん。**温めをオーナーとして走らせる**しか
  手がありません（`owner-todo.md` の「4」の相談）

おくようにしました（`lib/supabase/warm.ts`）。表は読みません——欲しいのは

## 16周目 — 「iPhone SE で3秒以上」を分解しました（9/8）

**主犯は、まだ貼っていただいていない 0-B（トークンの寿命）です。**
本番のアクセストークンを実際に読むと `exp - iat = 3600`（1時間）のままでした。
一方 0-A の pg_cron のほうは貼っていただけていて、`rsstube-warm-morning` が
active で並んでいます（`cron.job` を直に見て確認）。

### 3秒の内訳（実測を積み上げたもの）

| | 何に | 出どころ |
|---|---:|---|
| `/` →(307) | 393ms | 冷えた関数（14周目の実測） |
| `/auth/refresh` →(307) | 848ms | 同上 |
| `/` → 200 | 973ms | 同上 |
| iPhone の PWA 起動＋サービスワーカーの起動 | 数百ms | 実機でしか出ない（下記） |
| **合計** | **3秒超** | |

**Vercel はルートごとに別の関数**なので、トークンが切れているときの3本立ては
**コールドスタート3回**です。0-B を入れると1本になり、払うコールドスタートも
1回だけになります。

### リダイレクトは、温まっていても 300ms 取っています

実際のブラウザ（Chromium、CPU を4倍遅くして待ち時間 70ms）で、
`PerformanceNavigationTiming` から分解しました。

| | トークン生存 | トークン切れ |
|---|---:|---:|
| リダイレクト | 0ms | **303ms** |
| responseStart | 100ms | 404ms |
| first-paint | 168ms | 472ms |
| load | **320ms** | **647ms** |

**倍になっているのは全部リダイレクトのぶん**です。ページの組み立ても
hydration も、どちらも responseEnd から load まで約 160ms しかかかっていません。
**JS が重いのではありません**（12本・展開後 670KB ですが、中身は react-dom
224KB と Next のルーター 155KB で、削れるのは器のほうではない）。

### 昼も冷えていました（0-C）

日中の温めは5分毎のままです。1分刻みで測った冷め方は
**1分 96ms / 2分 263ms / 3分 553ms / 5分 554ms**——**3分でもう5分と同じ**でした。
「日中は使っている本人の操作が温め続けるので5分でよい」と書いていましたが、
**開く瞬間は、いつも使っていません**。今回3秒かかったのも朝ではなく昼です。
`supabase/scheduler.sql` を **2分毎**に直しました（貼るのは `owner-todo.md` の 0-C）。

### iPhone だけ、サービスワーカーの手当てが効いていません

`public/sw.js` は「fetch ハンドラがあると、起動が『ワーカーを起こす →
fetch()』の順になる」問題を **navigationPreload** で塞いでいますが、
**WebKit はこれに対応していません**（bug 182466。Chrome と Firefox だけ）。
つまり**手当てが効かない唯一のブラウザが iPhone** です。コメントにそう
書き足しました——ここを読んで「対処済み」と思わないように。
iPhone の起動を速くする手は**サーバー側**（往復を減らす・冷やさない）だけです。

手元の WebKit で確かめようとしましたが、Windows では `libsharpyuv.dll` が無くて
起動しませんでした（`playwright install webkit --force` まで試して駄目）。
なので上の数字は Chromium のもので、**サービスワーカーの起動ぶんは入っていません**。

### 結果 — 0-B と 0-C を入れていただいたあと（同日）

適用は本番で確認しました（JWT の寿命 `604800` = 7日、`rsstube-warm` が `*/2`）。

| | 合計 | 内訳 |
|---|---:|---|
| 前（冷えている＋トークン切れ） | **3029ms** | `/` 496ms → `/auth/refresh` 302ms → 本体 2230ms |

## 15周目 — 温めが5分毎では足りていませんでした（9/8）

14周目で入れた「5分毎に叩いて起こしておく」を、**冷えたところからもう一度**

|---|---:|---:|

### 認証はどこへ行ったか

proxy がやっていたのは「未ログインを弾く」と「セッションの更新」の2つで、
それぞれ移しました。

- **弾くのは各ページの入口**（`lib/auth/guard.ts`）。見るのは Cookie の期限だけで、

- **更新は `/auth/refresh`**。アクセストークンは1時間で切れるので、**朝いちばんの
  1回だけ**ここを通ります（更新して、開こうとしていた URL へ戻します。記事の
  URL をそのまま開いても、その記事に戻ります）。使っている間は、スター・あとで・
  既読などの操作が Cookie を書けるので自然に更新されます

**通した経路（本番で確認済み）**:

| | 結果 |
|---|---|
| ログイン済みで `/` `/settings` | 200 |
| ログイン済みで `/login` | 一覧へ戻す |
| 未ログインで `/` `/listen` | ログイン画面へ |
| 壊れた Cookie | ログイン画面へ |
| 期限切れで記事の URL を開く | 更新して、その URL へ戻る |
| 更新しても直らないとき | ログイン画面へ（往復し続けない） |
| `/api/opml` Cookie 無し / 有り | 401 / 200 |
| `/api/cron/poll` 秘密無し | 401 |
| `/manifest.webmanifest` `/sw.js` `/offline.html` | 未ログインでも 200 |

本番の iPhone 相当（WebKit）でも、期限切れの状態から開いて一覧が出るところ、
5画面を回るところ、記事を開いてスターが DB に入るところまで確認しています。

**もし朝いちばんにログイン画面が出たら**、それは更新トークンまで切れていた
（1〜2週間触っていない）ときです。パスキーかパスワードで入り直してください。
そうなっていないかは、この後もこちらで見ています。

## 7周目 — 夜のあいだにやったこと（9/7・本番に出ています）

### 速さ

**朝いちばんの回線で、触ってもいない記事を半メガ落としていました。**
本番のスマホ幅で数えたところ、一覧を開くと先読みが11本飛び、うち2本が
**記事のページ丸ごと**（実測 140.9KB と、長い議事録で 370KB）。出どころは
2つとも「押しそうだ」の読み違いでした:

- キーボードのカーソルは何もしなくても先頭に居るので、**開いた瞬間に先頭記事**を
  取りに行っていた（スマホでは j/k を使わないので、ほぼ確実に無駄になる）
- 本文ペインはスマホでは畳まれているだけで DOM には居るので、**一覧を見ている
  だけで「次の記事」**を取りに行っていた

人がカーソルを動かしてから／ペインが実際に見えているときだけ取りに行くように
しました。本番の iPhone 相当で **記事の先読み 2本 → 0本**。`j` を押せば今までどおり
取りに行くので、キーボードで読む速さは落ちていません。PC は変えていません。

**先頭記事の本文を待たずに一覧を出すようにしました。** 「何も選んでいないときは
先頭を出す」ぶんの本文は、一覧が返ってこないと行き先が決まらないので、
**一列に足される往復**でした。スマホでは畳まれていて見えないのに毎回払っていた
ぶんです。手元の本番ビルドで一覧の到着が 268ms → **208ms**（本文の到着は変わらず）。

**設定の「進み具合と使用量」を後ろに回しました。** `pipeline_status()` はこの画面で
いちばん遅い問い合わせ（他が往復の下限＋5〜15ms に対して＋70ms）なのに、
フィードの追加や朝の時刻と一緒に待っていました。設定の本体 285ms → **190ms**。

### 読みやすさ

- **記事のメニュー（☰）が本文に被っていたのをやめました。** 本文の上に浮かせて
  いたので、読んでいる行の右端 48px が常に隠れていました。下の帯
  （前の記事 / 次の記事）の中に入れてあります。指の届く場所は同じです
- **記事の1行目**（情報源 / 著者 / 日付 · N分 · 取得）を2行に分けました。情報源の
  名前は長いものが多く、スマホでは必ず折り返して日付が行の途中に散っていました。
  **情報源を押すと、その情報源の記事だけの一覧へ移ります**
- **一覧に「いま何の中を見ているか」を出しました。** 絞り込み中は名前が名札で出て、
  押せば外せます。0件のときの文面にも名前が入り（「◯◯ に未読はありません」）、
  広げる先のボタンが1つ出ます（「◯◯ のすべてを見る」「絞り込みを外して探す」）
- 一覧の行のメタが折り返して行の高さが揃わなかったのを直しました

### 分かったが、やらなかったこと

**画面遷移に必ず乗る 124ms のうち約80msは、Vercel が proxy（middleware）を
1回起こす費用です。** 手元で同じ proxy を通しても静的ファイルと差が出ない
（15.5ms 対 16.2ms）ので、こちらのコードは無料で、**80ms は器のほう**だと
確かめました。消すには認証をアプリ側へ移す（Server Component で検証し、
期限切れだけ Route Handler で更新する）ことになりますが、**失敗すると朝いちばんに
ログインし直しになる**ので、寝ているあいだに入れるものではないと判断しました。
入れるかどうかはご判断ください（毎回の遷移が 250〜350ms → 170〜270ms 相当）。

**JS の量は手がありません。** 一覧で落ちる 559KB のうち 380KB は React と Next の
本体で、こちらのコードは 119KB です。

## 5周目 — 起動の待ちを詰めました（9/7・本番に出ています）

**ホーム画面から開いたとき、画面に何か出るまでが 330ms 早くなりました。**

遅かったのはサーバーではありません。`/` はページ全体が1つの関数で、**DBの
問い合わせが全部終わるまで `<head>` を1バイトも出していませんでした**。
ブラウザは `<head>` が来るまで CSS（45KB）も JS も落とし始められないので、
「サーバーを待つ」と「ファイルを落とす」が一列に並んでいた形です。
サービスワーカーの先読みも静的ファイルのキャッシュも、**URL が分かってから
しか働けない**のでここは効いていませんでした。

本番（東京）の実測——応答を届いた順に時刻付きで読んだもの:

| `/` を開いたとき | 前 | 後 |
|---|---:|---:|
| CSS/JS の在りかが届く（＝落とし始められる） | 471ms | **142ms** |
| 記事の中身まで全部届く | 473ms | 248ms |

**変えていないページが動いていないことが、上の差が本物だという証拠です**
（`/listen` 256ms・`/exports` 257ms・`/settings` 376ms は、いまも
「最後の1バイトと `<head>` が同時」のまま）。

待っているあいだは、記事一覧の**枠だけ**が灰色の帯で出ます。数字も記事名も
下部タブの文字も出していません——押せない文字が出ていると、反応しないアプリに
見えるためです。

**画面の中の移動（タブを押す等）の見え方は変わりません。** 骨組みが挟まるのは
最初の1枚だけで、遷移では今の画面を出したまま待ちます（本番の iPhone 相当の
ブラウザで、押した前後に骨組みが出た回数を数えて 0 回）。

本番を WebKit（iPhone 13 の見立て）で開いて確認済み。コンソールのエラーは
ありません。測り直す口は `node --env-file=.env.local scripts/head-probe.mjs`。

**まだ残っているもの**: 起動のいちばん重い部分は、そのあとに落ちてくる JS
（全部で 816KB・圧縮前）です。2回目からはサービスワーカーが手元に持っている
ので効きませんが、**アプリを更新した直後の初回**はここが効きます。
`/library` `/listen` `/exports` `/settings` は今回の直しを入れていないので、
通知から `/exports` を開くような入りかたでは前のままです。

**指の下も軽くなりました。** 一覧の行を1行ずつ「変わっていなければ描き直さない」

## 毎朝のまとめは NotebookLM（8/31 決定）

**自動でやるのは「選抜 → Markdown → `/exports` に置く → 通知」まで。**
音声にするのは人が NotebookLM でやります。**毎朝の自前音声は自動生成しません**

「毎朝のもの」から「押したときだけの深掘り」に変わりました。

**.md をダウンロード** か **本文をコピー** → NotebookLM に貼る → **指示文をコピー**して

（「ソースを追加 → ドライブ → 選ぶ」だけになる）。繋がったら、朝のダイジェストを

## 自動で回っているもの

pg_cron から叩いています（`supabase/scheduler.sql`）。
**直近2日ぶんの実行記録を見て、5本とも失敗ゼロ**でした（worker は576回・poll と digest は48回ずつ）。

|---|---|---|

## RSS の無いページ — 実測（8/26）と方針（8/27）

`回復術士のやり直し` のように、**サイトがRSSをやめてしまった**ページがある。
「更新があったことが分かればいい」という要望に対して、10ページで実測した。
（この節は owner-todo.md から移した。指示ではなく調べた結果なので、こちらが置き場所。）

- **本文テキストのハッシュを比べる方法は使える。** 10ページ中10ページでハッシュが
  安定し（3秒あけて2回取って変化なし）、8ページで「フィードの最新記事の題」が
  ページ本文に出ていた＝更新で必ず変わる
- **生HTMLのハッシュは使えない。** 4ページ中2ページが3秒で変わった（広告枠）
- **登録するURLの選定がすべて。** ComicWalker は素のURLだと「第1話」が出たままで
  **新話が出ても変わらない**。`?episodeType=latest` を付けると最新話が出る
- **どのURLが良いかを自動で判定する方法は見つからなかった。**
  「最近の日付が本文にあるか」で判定を書いたら11件中3件を間違え、しかも
  「絶対に鳴らないURL」を合格と判定した

**方針（8/27、オーナーの判断）**: 作る。**更新があったことだけを知らせる。**
中身は取りに行かない（RSS が無いページから本文を組み立てようとすると、広告や目次を
本文として掴んで、要約まで巻き添えになる）。出しかたは**普通の記事と同じ形**にして、
一覧に1行増やす——「RSS が無いので中身は取れていません」と記事の中身として書く。
専用の画面も通知の種類も増やさないので、スター・あとで・既読がそのまま使える。

**まだ実装していない。**まず ComicWalker の `?episodeType=latest` 1本で試す
（次の更新は9月上旬の見込み）。

## 見送った判断

無理に作らなかったものと、その理由。

- **pgvector で重複記事をまとめる** — 作る前に測ったら、直近400件で似た記事は4組（約1%）
  だけでした。1%のために毎記事へ埋め込みを付けるのは割に合いません
- **外部の本文抽出API（Jina Reader）** — 実際に困っている2フィード（Aeon・東洋経済）で
  両方とも弾かれました。効くのは元々取れているサイトだけです
- **エラーページ判定の定型文マーカー** — 誤検出が多く、8件中4〜5件が本物の記事でした。
  代わりに「冒頭が毎回同じ」で判定しています
- **PGroonga の `&@~` 演算子** — 索引を張るだけで8.2倍速くなったので、いまはそこまで
- **DB を触るテストの追加** — テストは外部依存の無い純関数だけに絞っています。
  `0027` の SQL は、本番のデータで実際に流して確かめました（そのほうが証拠として強い）

## 8/27 に直したこと — 日付と要約

### 千葉県の103件に日付が入っていなかった

フィードが `<pubDate>Wed, 26 Aug 2026 17:00:00 JST</pubDate>` と書いてきますが、
**`JST` は JavaScript が解釈できません**（RFC 822 が名前で認めているのは
UT / GMT と北米の4つだけ）。取り込みも本文も要約も正常に通り、日付だけが
欠けていました。一覧は日付なしを末尾に置くので、**103件（全体の29%）が
リストの一番下に沈んでいました**。「新着なのに出てこない」としか見えません。

- `lib/feeds/date.ts` で名前のタイムゾーンを読み替えます（JST / JDT / KST のみ。
  `CST` や `IST` は国によって違う時刻を指すので入れません）
- **既存の行も勝手に埋まります**（`0030`）。取り込みのついでに、その回の取得に
  入っていた項目ぶんだけ日付を入れ直します。手で直す作業は要りません
- **実際に埋まったことを確認済み**: 日付なし103件 → **0件**

### 先回りできないので、欠けたら見えるようにしました

タイムゾーンの略号を全部先に登録することはできません（`MSK` `CEST` …）。
健康診断が「日付が無い」フィードを出すようにしたので、次に知らない略号の
フィードを登録しても設定画面に出ます。

### 要約が「本文が取得できない」で埋まっていた

タイトルしか無い記事に要約を頼むと、モデルは*入力の説明*を返してきます。
一覧にそれが並び、無料枠も1件ぶん使います。

プロンプトで禁じるだけでは足りませんでした（24件→5件までしか減らない）。
**素材が空なら呼ばない**のが正解で、積む側と渡す側の両方で弾くようにしました。
購読中のフィードでは**0件**になっています。
