## 8/26 に直したこと — 音声化が詰んでいた

**音声1本が `synthesizing`（合成中）のまま8日間止まっていました。**
5セグメント中4つまでできていて、最後の1つが Gemini の無料枠切れ（429）で
5回試して諦めた状態です。

壊れ方は「静かに壊れる」型でした。

| どこが | どうなっていたか |
|---|---|
| ワーカー | ジョブが諦めても、`media` の行を誰も `failed` に落とさなかった |
| 「聴く」 | ready でも failed でもない行を「生成中」とみなすので、**できあがり予定時刻を永久に出し続けていた** |
| 再生画面 | 同じ理由で「生成中」。失敗だと分かる場所がどこにも無かった |
| 「音声にする」 | 一意索引に当たるので、押し直しても「既に作ってあります」しか返らず**二度と作れない** |

直したもの（`0027_media_recovery.sql` と、それを呼ぶ側）:

- **見捨てられた音声を落とす** — 生きたジョブ（順番待ち・実行中）が1つも無くなった
  ものだけを `failed` にします。ワーカーが毎回、時間予算の外で必ず通ります。
  「何分経ったら」で判定しないのは、再試行のバックオフ（最大12時間）と食い違って
  まだ生きているものを殺すため
- **作り直せるようにした** — 「聴く」と再生画面に「↻ 作り直す」を出しました。
  **できているところは作り直しません。**上の1本なら、残り1セグメントだけをやり直します
  （台本づくりは1日20回しか叩けないので、全部やり直すと詰まった原因の枠切れを
  もう一度踏むことになる）
- **詰まっていた1本は、いま `failed` として見えています。**「↻ 作り直す」を押せば
  残り1セグメントから再開します

## 見送った判断

無理に作らなかったものと、その理由。

- **pgvector で重複記事をまとめる** — 作る前に測ったら、直近400件で似た記事は4組（約1%）
  だけでした。1%のために毎記事へ埋め込みを付けるのは割に合いません
- **外部の本文抽出API（Jina Reader）** — 実際に困っている2フィード（Aeon・東洋経済）で
  両方とも弾かれました。効くのは元々取れているサイトだけです
- **エラーページ判定の定型文マーカー** — 誤検出が多く、8件中4〜5件が本物の記事でした。
  代わりに「冒頭が毎回同じ」で判定しています
- **PGroonga の `&@~` 演算子** — 索引を張るだけで8.2倍速くなったので、いまはそこまで
- **DB を触るテストの追加** — テストは外部依存の無い純関数だけに絞っています。
  `0027` の SQL は、本番のデータで実際に流して確かめました（そのほうが証拠として強い）
