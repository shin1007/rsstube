# 踏んだ罠 — ジョブ・ワーカー・音声

lib/jobs/ · lib/media/ · 通知 を触るときに読む。索引は `CLAUDE.md` にある。

**ここに書くのは「決まったこと」ではなく「実際に壊れた話」だけ。**
同じ壊れ方をもう一度させないための記録なので、直し方だけでなく
「どう見えたか（何が起きているように見えたか）」を残すこと。

- **1回のワーカー実行は時間で切る。** 件数だけで絞っても、TTS は1セグメントに
  数十秒かかることがあり `maxDuration = 60` を超えると関数ごと落ちて、
  running のジョブが宙に浮く。`TIME_BUDGET_MS` を見ながら次の種類に進む前に
  切り上げる形にしてある。

- **VAPID 鍵を作り直すと登録済みの端末には二度と届かない。** 購読はブラウザ側で
  公開鍵に紐づくので、鍵を替えたら `push_subscriptions` を空にして端末ごとに
  登録し直すしかない。本番と手元で鍵を揃えること（別々に生成すると、
  手元で登録した端末には本番からの通知が届かない）。

- **`jobs` にはRLSポリシーが1つも無い。** 0005 で `jobs_owner` を落として以来、
  ジョブを積めるのは Secret キーだけ（ユーザーに他人のジョブを見せない・作らせない
  ため、意図してそうしてある）。ログイン中のユーザーのクライアントで
  `enqueue()` すると 42501 で必ず弾かれる。`requestMedia()` がこれをやっていて、
  **「音声にする」は media の行だけ作って script ジョブを積まずに落ちていた**。
  しかも一意索引のせいで押し直すと「既に作ってあります」になり、永久に queued の
  行が残る。ジョブを積むのは `createAdminClient()` から。

- **スライドは文字だけ、と気づかれない。** 中身（見出し・箇条書き）は正しく出て
  いても、罫線も色も番号も絵も無いと「スライドが出ていない」と読まれる（実際に
  そう報告された）。0025 で記事の `image_url`（og:image / RSS の enclosure）と
  `media.cover_path` を足し、表紙の絵と差し色・枚数表示を入れてある。
  **画像URLを直接 `<img>` に貼らないこと。** 相手のサイトに毎回取りに行くことに
  なるし、記事が消えると絵だけ先に欠ける（音声は14日残る）。Storage へ写す
  （`lib/media/cover.ts`）。写すのは media 1本につき1枚だけ——全記事ぶん溜めると
  Storage の無料枠(1GB)を音声と奪い合う。

- **後から全記事を浚う処理を足さない。** `image_url` を後付けするとき、既存の
  未設定が2024件あった。表紙が要るのは音声にする1本だけなので、要るときに
  先頭3件まで取りに行って記事側へ書き戻す形にしてある（`resolveCoverUrl`）。
  同じ判断は他の後付け列にも効くはず。

- **引いたジョブを全部処理しないなら、その場で戻すこと。** `claim_jobs` は返す前に
  `running` にして `attempts` を +1 する。ワーカーは `TIME_BUDGET_MS` を見ながら
  回るので**引いた数と処理した数は一致しない**（TTS は1回で1〜2件しか進まない）。
  手を付けなかったぶんは 0004 の拾い直し（15分）を待つことになり、
  「2件進んでは15分待つ」で完成が異常に遅くなる。しかも拾い直しのたびに
  `attempts` が増えるので、**一度も実行されていないジョブが5回の空回りで
  failed に落ちる**（実際に tts が5件この状態になっていた）。
  `release_jobs`（0026）で即座に戻す。時間切れは失敗ではないので attempts も戻す。

- **待ち時間の見当は件数の上限からではなく実測から出す。** `TTS_PER_RUN` は4だが、
  時間予算のほうが先に来るので実際は1〜2件。上限を使うと出した時刻を過ぎても
  終わらず、何も出さないより悪い（`lib/media/eta.ts`）。

- **ジョブが諦めたら、それを待っている行も誰かが落とすこと。** `markFailed` は
  429・503 で `media.status` を意図して動かさない（1セグメント転んだだけで全体を
  殺さないため）。正しいが、**ジョブが `max_attempts` で failed に落ちたあとに
  media を落とす人がどこにもいなかった。**結果、`synthesizing` のまま8日残った1本が、
  `/listen` では「合成中」＋できあがり予定時刻を永久に出し続け、failed ではないので
  再試行の導線も出ず、一意索引のせいで「音声にする」を押し直しても
  「既に作ってあります」しか返らなかった（＝**手の出しようが無い**）。
  `0027` の `fail_abandoned_media()` が「生きたジョブが1つも無い」を死亡判定にして落とす。
  **経過時間で判定しないこと。** `fail_job` のバックオフは最大12時間あるので、
  まだ生きているものを殺す。

- **作り直しは、できている途中まで残して再開する。** 台本は1日20回、合成もセグメント
  ごとに無料枠を食う。全部やり直すと、詰まった原因が枠切れだったときに同じ枠切れを
  もう一度踏む。`retry_media()`（`0027`）は諦めたジョブの `status` を戻すだけで、
  payload を作り直さない。`jobs_pending_unique_idx` は `payload ->> 'article_id'` を
  見るので、`article_id` を持たない script / tts の重複はDBでは防げない。
  積む前に「生きたジョブがあるか」を自分で見ること。
