# 踏んだ罠 — 速さ

proxy · 遷移 · 運ぶ量 を触るときに読む。索引は `CLAUDE.md` にある。

**ここに書くのは「決まったこと」ではなく「実際に壊れた話」だけ。**
同じ壊れ方をもう一度させないための記録なので、直し方だけでなく
「どう見えたか（何が起きているように見えたか）」を残すこと。

- **遅さは、まず「ページを描く前」を測ること。** 記事を開くのが遅いと言われて
  一覧の描き方ばかり見ていたが、実際にいちばん重かったのは `proxy.ts` だった。
  ログイン済みで `/login` を叩くと middleware が 307 を返して終わる（ページ描画
  ゼロ）ので、これが proxy だけの値になる。本番・東京の実測:
  静的ファイル16ms / proxy だけ **250ms** / `/` を開く570ms ——**待ち時間の
  4割強が認証の1往復**だった。`getUser()` は Supabase の Auth に毎回聞きに行く。
  署名鍵が非対称（このプロジェクトは ES256。`/auth/v1/.well-known/jwks.json` で
  確かめられる）なら `getClaims()` が WebCrypto でその場で検証するので往復が消える
  （鍵は auth-js の `GLOBAL_JWKS` にプロセスごと残る。温まった関数では0回）。
  実測 250ms → 116ms。**検証は緩んでいない**——`getSession()` を信じるのとは違い、
  署名を照合し `exp` も見る。対称鍵や WebCrypto の無い環境では auth-js が
  自分で `getUser()` に落ちる。トークンの更新も getClaims の中の getSession が行う。

- **走っている途中の先読みは、遷移には使われない（Next 16 のセグメントキャッシュ）。**
  `navigateImpl` が再利用するのは `EntryStatus.Fulfilled` の項目だけで、Pending は
  素通りして自分でもう1本取りに行く（`segment-cache/navigation.js`）。つまり
  **押した瞬間に先読みを始めても間に合わない**——同じページをサーバーが2回組むだけ。
  マウスなら `pointerenter` で数百ms稼げるが、指には「載せる」が無いので、
  スマホの一覧→記事は先読みでは速くできない。速くするなら運ぶ量を減らすほう。

- **一覧は、画面に出していない列を毎回運んでいた。** 記事は `?article=` の
  付け替えで開くので、1回開くたびに一覧がまるごと運び直される（実測61KB / 24行）。
  中身を数えたら `url` `author` `content_ok` `tags` は行のどこにも出しておらず、
  `excerpt` は要点があるときは出さない側なのに常に付いてきていた（日本語で150字
  ほどあり、1行でいちばん重い）。**出していないものは運ばないこと**——`ArticleRow` の
  それらは `?` にして、実際に出している `/library` だけが渡す。53KB に減った。
  列を1つ足すときは「どの画面のどこに出るか」を先に決める。出さないなら足さない。

- **記事の遷移が遅いのは、`/` を毎回まるごと作り直しているから。** 記事は
  `?article=` の付け替えで開くので、1回の遷移がサイドバー＋一覧60件＋本文の
  再構築になる。実測で RSC 89KB（転送26KB）・Supabase に6往復。中身のうち
  変わっているのは本文だけで、**運んでいるものの大半は一覧のほう**（要約の箇条書きが
  日本語で入るため。本文HTMLは平均21KBだが、記事1本ぶんの重さより一覧60件が重い）。
  DBは速い（実測 1〜17ms）ので、遅さは往復と量から来ている。ここに3つ重なっていた:
  - **`revalidatePath('/')` は「ページ全体を描き直した RSC」を Server Action の
    応答に積んで返す**（呼ばなければ描き直さない。`action-handler.js` の
    `skipPageRendering`）。開いた拍子の既読がこれを連れていたので、
    **1タップにつき遷移と同じ重さの描き直しがもう1回**走っていた。
    見せる変化がある操作（スター・あとで・手の既読）だけ revalidate する。
  - `MarkReadOnView` が同じ記事にもう1通 markRead を投げていた。開くのと
    既読の書き込みは同時に走るので、**本文を描く読み取りが勝つと `is_read` は
    まだ false** で返り、二度目が止まらない。`lib/read-marks.ts` に送った id を
    覚えて止める。既読の見た目もそこから一覧へ配る（revalidate をやめたので、
    サーバーの描き直しには頼れない）。
  - **`router.prefetch(href)` は動的ルートでは何もしない。**既定は `kind:'auto'`
    で、`loading.js` の境界までしか取らない＝`/` には境界が無いので**要求が
    1本も飛ばない**（3秒待って通信ゼロ。効いているつもりで何も起きない）。
    `kind:'full'` を渡すこと（`lib/prefetch.ts`）。`<Link prefetch>` も同じ意味。
    先読みしたぶんは静的扱いで5分残るので、「次の記事」は**往復ゼロ**で切り替わる。
    先読みは行きそうな1件だけにする——1件ごとにサーバーがページを丸ごと組む。
    **`revalidatePath` は先読みも一緒に捨てる**ので、読み進める経路で revalidate を
    呼ぶと待ち時間がそのまま戻ってくる。
  副作用として、サイドバーの未読数は開いた記事1件ぶん遅れて減る（次の描画で追いつく）。
- **埋め込みの入れ子ひとつで7倍遅くなる。** 一覧を購読しているフィードだけに
  絞るのに `feeds!inner (subscriptions!inner (folder_id))` と入れ子で書いていた。
  正しいのだが、**未読一覧の問い合わせが 227ms、外すと 31ms**（本番相当の実測）。
  埋め込みは1つ増えるごとに横結合が増え、Supabase の無料枠では計画だけで
  数十msかかる（`EXPLAIN` で計画44ms・実行61ms）。購読は12本しかないので、
  `feed_id` を先に引いて `in (…)` で絞るほうが速い（`subscribedFeedIds()` は
  React の `cache()` に包んであるので、一覧・件数・前後の id が同じ絞り込みを
  使っても問い合わせは1リクエストに1回）。
  **測り方はこう。** ①静的ファイルを叩いて往復の下限を出す ②`/login` に
  ログイン済みで入って 307 だけ返させ、proxy だけの値を出す ③問い合わせを
  1本ずつ手元から叩き、①を引く ④怪しいものは select から1つずつ外して差を見る。
  ④が効いた——「一覧が重い」ではなく「入れ子の1行が重い」まで絞れる。

- **並列に投げているものは、いちばん遅い1本しか効かない。** 認証の往復（250ms）と
  一覧の問い合わせ（227ms）を潰したら、`/` は 594ms → 402ms になった。減ったのは
  192msで、2つの合計（約350ms）ではない。**残りはページを組んで RSC を流す時間**
  （TTFB 195ms・完了まで 400ms）で、そこはDBを速くしても動かない。
  次に削るなら運ぶ量か、組み立てそのものを減らすほう。

- **全ページに乗っている1往復は、呼び出し元を見ないと見つからない。**
  `listSubscribedFeeds()` が `feed_content_stats()`（直近60日の記事を全部数える
  集計・サーバー側50ms）を**無条件に、しかも購読の取得の後ろで直列に**
  await していた。関数の中だけ見れば「フィード一覧にくっついた数字」でしかない。
  ところがこの関数はサイドバー（AppShell）が持っているので、**設定を開いて
  いないときも全ページの遷移に丸ごと乗っていた**。数字を使うのは `/settings` の
  FeedHealth だけ。ぶら下げるときは「誰がこの関数を呼ぶか」を先に見ること。

- **PostgREST の exact count は、DB が数えるより一桁高い。**
  設定画面の「取り込みの進み具合」は `count: 'exact', head: true` を3本
  投げていた。並べてはいたが**3本とも articles ⋈ article_states を丸ごと
  数える同じ走査**で、違うのは filter だけ。実測 27ms / 63ms / 127ms で、
  いちばん遅い1本がそのまま待ち時間になる。同じ数え方を素の SQL で
  `explain analyze` すると **6ms**だった——遅いのは DB ではなく、埋め込みを
  含む count を PostgREST が組み立てるほう。`filter (where …)` を並べた
  関数1本にまとめれば走査も1回で済む（0038 の `pipeline_status()`）。

- **ログインの確認は、ページだけでなく「押すたび」にも乗っている。**
  proxy を `getUser()` → `getClaims()` にしたのに、Server Action は
  `getUser()` のままだった。**スター・あとで・既読は押すたびに Server Action を
  1本呼ぶ**ので、往復ぶん（実測で約134ms）がそこにも乗り続けていた。
  `lib/auth/session.ts` の `currentUser()` に寄せてある。**id しか要らない
  ところで getUser() を書かないこと**——欲しいのはたいてい `user.id` で、
  それは検証済みの JWT の `sub` に入っている。

- **同じ1行を2回読んでいないか。** `driveStatus()` は `googleOAuth()` で
  app_config を読み、その直後に `storedClientId()` で**同じ行をもう一度**
  読んでいた。しかも直列で、後ろに google_accounts が続く。関数に分けると
  1回ぶんに見えるので、呼ぶ側に並べてみるまで気づけない。

- **直列の数珠つなぎは、1本ずつ見ると正しく見える。** `getPlayable()` は
  media → セグメント → 署名 → **表紙の署名** → もとの記事、と最大5往復が
  数珠つなぎだった。前を待つ必要があるのは署名（path が要る）ともとの記事
  （kind / digest_id が要る）だけ。表紙は別のバケットではないので、
  セグメントと同じ `createSignedUrls()` 1回に入れられる。
  実測 350ms → 237ms。

- **proxy に残っている時間は、proxy の仕事ではない。** `/login` にログイン済みで
  入って 307 だけ返させると 120ms（静的16ms / proxy 対象外の関数 38ms）。
  ここから「まだ認証が重い」と読みたくなるが、**Cookie を1つも送らずに同じ口を
  叩いても 111ms** だった——`getClaims()` が本当に使っているのは差の10ms弱で、
  残りは **Vercel が middleware を1回起こす費用**。こちらのコードでは動かせない。
  「proxy が遅い」と「proxy を通る道が遅い」を混同しないこと。

- **索引が使われていても速いとは限らない（検索）。** リーダーの検索
  （`title / title_ja / content_text` の ilike）は 0015 の PGroonga 索引を
  ちゃんと使っている（BitmapOr が4.5ms）。それでも 105ms かかるのは、
  そのあとの **Bitmap Heap Scan の recheck が1199行ぶんの `content_text` を
  取り出して ilike をやり直す**ため（613ブロック・99ms）。しかも索引側は
  購読も既読も見ないので、**捨てる行のために本文を読み出している**。
  直すなら「絞ってから当てる」形（購読と未読で先に絞る）が要るが、
  それは絞り込みと並び順を SQL に二重化することになる（`applyFilters` を
  1か所にまとめてある理由と衝突する）ので、**いまは直していない**。
  直すときは、まず `explain (analyze, buffers)` で recheck の行数を見ること。

- **測り直せるようにしておくこと。** `scripts/perf-probe.mjs` が上の手順
  （静的 → proxy 対象外の関数 → proxy だけ → 各ページの HTML と RSC）を
  そのまま実行する。セッションは Secret キーで作るのでパスワードは要らない。
  **1回目は捨てて中央値を取る**——冷えた1回目には関数の起動と JWKS の取得が
  乗る。それでも run ごとに ±30ms は動くので、**30ms 未満の差を「速くなった」と
  書かないこと。**

- **「並べてあるから速い」は、往復の本数を無視している。** 外枠（サイドバーと
  下部タブ）が要る4つ——`folders` / `subscriptions`+`feeds` / `unread_counts()` /
  未聴の数——は `Promise.all` で並べてあった。並んでいる以上いちばん遅い1本しか
  効かないはずだが、**素の SQL で測ると4本とも 0.5ms 前後**で、まとめて1本に
  しても 2.7ms しかかからない。つまりここで払っていたのは実行時間ではなく、
  **HTTP の往復と PostgREST が問い合わせを組み立てる費用を4回ぶん**だった。
  1本にまとめて `/` の最初の1枚が 343ms → 282ms、`/library` が 359ms → 316ms。
  「DB が遅いのか、その手前が遅いのか」を先に分けること（`explain` の
  実行時間と、アプリから見た時間の差がそれ）。

- **運ぶ量を半分にしても、速くならないことがある。** 一覧の1ページ目を
  60件から30件に下げた。RSC の中身は 92KB → 60KB（行のぶんは 74KB → 42KB で
  ほぼ半分）まで減ったのに、**「すべて」の遷移は 340ms → 350ms で変わらなかった**。
  下げる前に「60行ぶんで約96ms」と見積もっていたのは、同じ run の中で
  `/`（21KB・332ms）と `/?view=all`（92KB・428ms）を並べて引き算した数字で、
  **量の差と決めつけていたが、実際には問い合わせの差でもあった**
  （`?view=all` は未読の絞りが無いぶん count が重い）。
  **2つの画面の差を、そのまま1つの原因に割り当てないこと。** 確かめるには
  同じ画面で片方だけ変えて測る（そして今回それをしたら、差は出なかった）。
  **60件に戻した。** 速くならない変更のために1ページ目を短くする理由は無く、
  長いほうがスクロールの継ぎ足しが減る。**もう一度下げようとしないこと**
  ——`lib/types.ts` の `PAGE_SIZE` にも同じことを書いてある。

- **索引が効いていても遅いなら、演算子を疑う（続き）。** 上の「索引が使われて
  いても速いとは限らない」の答えは `ilike` をやめることだった。PGroonga の
  `&@` は索引の中で決まるので、**Bitmap Heap Scan の recheck が要らない**
  ——本文を取り出して照合し直すぶん（1199行・99ms）がまるごと消える。
  実測 125ms → 38ms（往復の下限が35msなので、実質90msがゼロに）。
  **当たる件数は減らない。** 実データで11語を突き合わせて9語は同数、2語は
  `&@` のほうが多かった（`AI` 89→93、`令和8年` 312→377。全角半角と大小文字を
  正規化するため）。「整脈」「ンター」のような語の途中も bigram なので当たる。
  PostgREST は `&@` を書けないので RPC が要るが、**絞り込みまで SQL に
  移さないこと**——`search_article_ids()` が返すのは「自分の記事のうち
  当たった id」だけで、未読・スター・フォルダ・並び順は `applyFilters` の
  ままにしてある（一覧・件数・前後の id は `cache()` で同じ id 集合を使う）。
  id を `in.(…)` で URL に並べるので上限が要る。**実測で300件（約11KB）まで
  通り、500件（約19KB）は `fetch failed` で接続ごと落ちた**ので 250 で切ってある。
  副作用として検索語は POST の本体で渡るようになり、URL に3回並べていた頃の
  「WAF に弾かれて500」が起きなくなった。

- **`<Suspense>` の中に置いても、prerender は境界の中まで入ってくる。**
  Cache Components に移して `/` の一覧と本文を境界の中へ入れたのに、
  dev の検証が `Route "/": unstable value Date.now()` で止めてきた。踏んでいたのは
  **supabase-js がトークンの期限を見る `Date.now()`** で、`cookies()` を読むより
  先に来るので「先に動的なものを触らせる」では避けられない。境界は
  「ここから遅れてよい」の印であって「ここから先は見ない」ではない。
  止めたいところには `connection()` を置く（migrating-to-cache-components の
  「Fix synchronous IO. It can't be deferred.」）。
  **ただし下の項も読むこと**——この `connection()` は本番で別の壊れ方をした。

- **手元の本番ビルドで通っても、Vercel では落ちる（もう一度踏んだ）。**
  上の `connection()` を入れて、`next build` + `next start` をブラウザで
  操作して確認まで済ませたのに、**本番だけ `/` が error.tsx に落ちた**。
  サーバーが返す HTML は正常（サイドバーも一覧も入っている）で、
  **ブラウザ側で React #441**（＝サーバー側で投げた何かが digest に化けたもの）。
  つまり**最初の1枚を curl で見ても気づけない**——押して初めて分かる。
  戻して本番の健全を先に取り戻した。`docs/status.md` の出し方の「本番で1回
  動かす」は、**curl ではなくブラウザで**という意味だと考えること。

- **Partial Prefetching では `<Link prefetch={true}>` を並べない。**
  既定の `<Link>` が取るのは**ルートごとに1つの App Shell**（何本リンクが
  あっても1回、しかも共有される）。`prefetch={true}` はそこに「そのリンクの
  URL ぶん」を足す指定で、**見えているリンク1本につきサーバーが1回起きる**。
  サイドバーはフィードとフォルダで20本前後あり、飛び先はどれも同じ `/`
  （違うのは searchParams だけ）。つまり画面を開くたびに20回叩いていた。
  以前は付けるのが正しかった（`router.prefetch` の既定が動的ルートで何も
  しなかったため。上の項）が、**Partial Prefetching を入れた時点で前提が
  入れ替わっている。前に書いた罠が、次の版で逆になることがある。**
  外しても速さは変わらない（押してからサイドバーが出るまで 13〜29ms →
  14〜20ms。効いているのは App Shell のほうだった）。

- **サーバーで日時を文字にするときは時間帯を渡す。** `toLocaleString('ja-JP')`
  に `timeZone` を渡さないと、動かしている機械の設定で決まる。手元は日本時間
  なので正しく見えるが、**Vercel は UTC** なので本番だけ9時間ずれる。
  「取得 12:07」が「取得 3:07」になる形で、**それらしい時刻が出るぶん
  壊れているとは分からない**。見つかったのは Cache Components に移したとき
  ——時間帯の無い `toLocaleString` は prerender では答えが決まらないので、
  同期IOとして弾かれた。集めてあるのは `lib/datetime.ts` の `JST`。
  ブラウザ側で出しているところは読む人の時計でよいので渡さない。

- **速くするために入れたものは、壊れたら戻す。**（2026-09-06。Cache Components）
  `cacheComponents` + `partialPrefetching` を入れて、押した瞬間にサイドバーが
  出るところまで行った（本番のブラウザで実測 12〜26ms）。ところが**実機の
  iPhone で「画面を出せませんでした」**——error.tsx に落ちた。こちらの手では
  再現しなかった: サーバーが返す HTML は正常、curl も 200、Chromium は
  スマホ幅でも通る。出ていた手掛かりは本番のコンソールの React #418
  （hydration の文字の食い違い）だけで、それも Chromium では復帰していた。
  **毎朝読むアプリなので、原因の分からない不具合を抱えたまま置かない。**
  丸ごと戻した。速さは前の日の値（押してから250〜380ms）に戻るが、
  そこは動いている。
  次に入れ直すときの持ち帰り:
  - **Chromium だけで確かめない。** iPhone は WebKit で、手元には入っていない
    （`npx playwright install webkit` が要る）。ここを揃えるまで、
    この種の作り替えは「確かめた」と言えない
  - `Date.now()` の prerender エラー（supabase-js がトークンの期限を見る）を
    `connection()` で潰したら、**本番だけ React #441** で落ちた。手元の
    本番ビルドでは出ない。`connection()` と runtime prefetch の組み合わせが
    怪しいが、確かめられていない
  - **日時の時間帯の直しだけは残した**（あれは Cache Components とは無関係の、
    本番だけ9時間ずれていた実害）

- **サーバーとブラウザで時間帯が違うと、hydration が食い違う。**
  `'use client'` のファイルでも**最初の1枚はサーバーで描かれる**。
  `ArticleList` の「取得」時刻は `toLocaleString('ja-JP')` に時間帯を
  渡していなかったので、**サーバー（Vercel は UTC）と手元のブラウザ
  （日本時間）で別の文字**になり、React が食い違いとして弾いていた
  ——本番のコンソールにずっと出ていた `Minified React error #418` の正体。
  手元で `next start` するとサーバーも日本時間なので**一致してしまい、
  再現しない**。`TZ=UTC npm start` で本番と同じ条件になる。
  時間帯を渡したらエラーは0件になった（WebKit・iPhone 13 の見立てで確認）。
  **クライアントで出すぶんは時間帯を渡さなくてよい、は誤り**——
  SSR がある限り、サーバーとブラウザの両方で同じ文字にならないといけない。

- **iPhone の不具合は WebKit で見ること。** Playwright の chromium しか
  入れていなかったので、スマホ幅にしても engine は Chromium のままだった。
  `npx playwright install webkit` を toolbox で1回入れておく。
  `devices['iPhone 13']` と合わせると、`pageerror` が本物の Safari と
  同じ形で拾える。**幅を変えることと、engine を変えることは別。**

- **件数を別の1本で数えていた（それが毎回いちばん遅かった）。** 一覧の
  「あと何件」は `countArticles()` が `count: 'exact', head: true` で数えていて、
  一覧の取得と `Promise.all` で並べてあった。並んでいるのだから待ち時間は
  「いちばん遅い1本」……そのいちばん遅い1本がこれだった。手元からの実測
  （往復の下限 60〜78ms）:

  | | 一覧だけ | 一覧＋`count` 同梱 | 件数だけ（`head: true`） |
  |---|---:|---:|---:|
  | 未読 | 79ms | **79ms** | 112ms |
  | すべて | 120ms | **116ms** | 128ms |

  **同じ問い合わせに載せると増えないのに、別に投げると1本ぶん丸ごとかかる。**
  払っていたのは走査ではなく、PostgREST がもう1本組み立てて往復するほうだった
  （上の「exact count は DB が数えるより一桁高い」と同じ話）。
  `listArticles()` が `{ articles, total }` を返す形にして、口を1つにまとめた。
  ついでに「同じことを数える口が2つある」状態も消えた——**ずれると
  「あと12件」と出しておきながら3件目で終わる**、という形で表に出るところ。
  - **`count` を頼むのは1ページ目だけにすること。** `count: 'exact'` を付けると、
    範囲が総数を追い越したときに PostgREST が **416（PGRST103）** で落ちる。
    付けない同じ問い合わせは 200 と空配列で返る（実測: offset=5000 で 416 / 0件）。
    無限スクロールの継ぎ足しは終わりを「返ってきた数が1ページに満たないこと」で
    見ているので、ここで投げると一覧の末尾に「読み込めませんでした」が出る。

- **一覧の行は memo する（React Compiler は入っていない）。** `ArticleList` は
  指の操作のたびに描き直す部品を1つの関数に全部持っていた——引っぱって更新は
  `touchmove` ごとに `setPull`、帯（flash）・ヘルプ・ドロワー・カーソル移動も
  それぞれ state。**そのたびに一覧の全行が丸ごと描き直し**になっていた。
  コード中のあちこちに「React Compiler の求めるまま」と書いてあるが、あれは
  eslint の規則の話で、**`next.config.ts` に `reactCompiler` は入っていない**
  （＝実行時に畳まれてはいない）。手元の本番ビルドで j/k を80回叩いた実測:

  | 一覧の行数 | 前（1回あたり） | 後 |
  |---|---:|---:|
  | 60行（1ページ目） | 中央値 32ms・最大 222ms | **16.7ms**（＝1フレーム。上限に張り付き） |
  | 240行（3回継ぎ足し） | 中央値 111ms・最大 662ms | **16.6ms** |

  `memo` は**渡すものが毎回同じでないと素通りする**ので、行ごとの
  `() => ...` を props から追い出し、位置（index）と id を行から渡し返す形にした
  （`ArticleListRow`）。一覧そのものを見る操作（「ここから下を既読」）は
  `useLatest` の箱越しに読む——`useCallback([rows])` にすると、既読を1件
  付けるたびに関数が作り直されて memo が全部外れる。
  **測り方**: `requestAnimationFrame` を挟みながらキーを撒いて1フレームの
  長さを測る。16.7ms に張り付いていれば描画は上限（vsync）待ちで、
  そこを超えていればこちらの描き直しが1フレームに収まっていない。

- **動的なページは、最初の `await` が終わるまで `<head>` すら出ない。**
  ホーム画面から起動して真っ暗な数秒のあいだ、通信は何もしていなかった。
  `/` は `force-dynamic` で、ページ全体が1つの `async` 関数だったため、
  React が `<html>`／`<head>` を流し始められるのが**全部の問い合わせが
  終わったあと**だった。本番（東京）の実測——応答を chunk ごとに時刻付きで
  読んだもの:

  | | ヘッダ到着 | `</head>` 到着 | 最後 |
  |---|---:|---:|---:|
  | `/` | 471ms | **471ms** | 473ms |
  | `/library` | 375ms | 375ms | 379ms |

  **`</head>` が最後と同時**＝ブラウザが CSS（45KB）と JS を落とし始めるのが
  そこから。サービスワーカーの navigationPreload も静的ファイルのキャッシュも、
  **URL が分かってからしか働けない**ので、この直列は消せていなかった。
  「サーバーは 470ms しかかかっていない」は、起動の体感とは別の数字。

  直しかたは、ページ本体を `<Suspense>` に入れて、**入れ子の外側を `async` に
  しない**こと（`app/page.tsx` の `ReaderPage` → `Reader`）。`searchParams` を
  そこで `await` すると元に戻るので、Promise のまま中へ渡す。手元の本番ビルドで
  `/` は `</head>` が **20ms**（最後は 349ms のまま）。**変えていない
  `/library` 225ms・`/listen` 171ms が動いていないことが、効いている証拠。**

  - **画面遷移の見え方は変わらない。** 遷移は transition の中で起きるので、
    React は新しい中身が揃うまで今の画面を出したままにする。`/listen` から
    `/` を押して MutationObserver で `[aria-busy]` を数えた実測で 0 回

  - **`loading.tsx` は置かないこと。** あれはルートの境界になるので、
    **押すたびに骨組みが挟まる**（いま出ている一覧が消える）。ここで欲しいのは
    最初の1枚だけの話。
  - fallback に本物の値を出さない（`docs/traps/ui.md`）。灰色の帯だけにして、
    数字も記事名も下部タブの文字も出していない。押せない文字を出すと、
    反応しないアプリに見える。

- **`<Suspense>` は全ページに要る（`/` だけでは足りない）。** 上の直しは
  リーダーだけに入れたが、二次画面も同じ作りだった。手元の本番ビルドで
  `</head>` の到着が `/library` 287→**19ms**、`/settings` 274→**15ms**、
  `/listen` 165→**15ms**、`/exports` 168→**10ms**。fallback は
  `components/Skeleton.tsx` にまとめてある（外枠は `AppShellSkeleton`）。

- **測る前に、手元のサーバーを立て直したか確かめること。** 直したあとに
  `next start` を叩いたら `EADDRINUSE` で**前の版が生き残ったまま**応答していて、
  「入れたのに1ページも速くなっていない」という誤った結論を1回出した。
  `&` で後ろに回すと起動の失敗が目に入らない。`.next/start.log` を見るか、
  ポートを掴んでいるプロセスを先に落とす。

- **「押しそうだ」の先読みは、押す気配を確かめてから。** 本番のスマホ幅で数えたら、
  一覧を開いた時点で先読みが11本飛んでいて、うち2本が**記事のページ丸ごと**
  （実測 140.9KB と 370KB）。どちらも人が何もしていない状態で出ていた:
  - **キーボードのカーソルは初期値で先頭に居る。** 「カーソルの下を先読み」は
    正しいが、初期位置は「開きそう」の合図ではない。人が動かしてから（j/k・
    行のフォーカス）にする。
  - **畳まれている要素の effect は動く。** 本文ペインは `hidden md:flex` で
    見えないだけで DOM に居るので、一覧を見ているだけで「次の記事」を
    取りに行っていた。`offsetParent === null` で畳まれているかが分かる。
  - **手元の `next start` と本番で、先読みの中身が違う。** 手元では小さな画面の
    先読みも中身ごと返る（/listen が 18KB）が、本番の Vercel では 0.3KB の
    スタブしか返らないものがある。**先読みの重さは本番で数えること。**

- **Vercel の proxy 80ms は、こちらのコードの費用ではない。** 手元の `next start` で
  proxy を通した 307（15.5ms）と、proxy を通らない静的ファイル（16.2ms）に差が
  無かった。`getClaims()` は JWKS がプロセスに残るので往復ゼロ——つまり本番の
  「proxy だけ 124ms」対「関数だけ 43ms」の差は**器を1回起こす費用**で、
  中身を削っても減らない。消すなら proxy そのものを無くす（認証を Server
  Component へ移し、期限切れの更新だけ Route Handler でやる）しかないが、
  失敗が「朝いちばんにログインし直し」として出るので、入れるなら起きている日に。

- **proxy を消した（2026-09-07）。上の項の続き。** 見当どおり、**画面遷移の
  TTFB が 130〜145ms → 40〜60ms** になった（本番・中央値）:

  | | 前 | 後 |
  |---|---:|---:|
  | `/` 未読（RSC） | 249ms（TTFB 141） | 236ms（TTFB **57**） |
  | `/` すべて | 352ms（136） | 261ms（**53**） |
  | フィード絞り込み | 240ms（138） | 143ms（**43**） |
  | 記事を開く | 317ms（133） | 248ms（**44**） |
  | `/listen` | 236ms（129） | 152ms（**44**） |
  | `/exports` | 246ms（131） | 154ms（**40**） |
  | `</head>` の到着（`/`） | 142ms | **56ms** |

  移し先は `lib/auth/guard.ts`（未ログインを弾く）と `/auth/refresh`（更新）。
  **やってはいけないこと**が2つあるので、触るときは必ず両方を守ること:

  - **Server Component でトークンを更新させない。** `getClaims()` /
    `getSession()` は期限が切れていると自分で更新しに行くが、Server Component
    からは Cookie を書けないので**新しい更新トークンが捨てられる**。更新トークンは
    使うたびに回転するので、捨て続けると Supabase の reuse interval を過ぎた
    時点でセッションごと死ぬ（＝二度と入れない）。だから guard は**期限を
    自分で読むだけ**にして、切れていたら書ける場所（Route Handler）へ送る。
  - **guard で署名を照合しない。** 照合は WebCrypto でできるが、冷えた関数では
    JWKS を取りに行くので、先に流している `<head>` がその往復ぶん遅れる。
    ここは「ログイン画面へ送るか」を決めるだけで、**読み書きの可否は RLS が
    決める**（Supabase 側が同じトークンを自分で検証する）。Cookie を書き換えれば
    枠は出せるが、中身は1行も取れない。

  **確かめる経路は6つ**（`docs/status.md` の8周目に表がある）: ログイン済み /
  未ログイン / 壊れた Cookie / 期限切れ→更新→戻る / 印を持ったまま期限切れ /
  API（opml・cron・passkeys）。新しい画面を足したら `requireSession()` を
  呼ぶこと——呼び忘れても RLS が中身を止めるので穴にはならないが、
  未ログインの人に空の画面が出る。

- **DB の仕事と、往復の本数を分けて測ること。** 一覧が遅いと言うとき、
  遅いのはたいてい問い合わせではない。本番のデータ（記事4875件・購読12本）に
  直に繋いで計ると、素の `select 1` が 34.3ms で、**その上に乗るのは**
  購読の feed_id が 0.2ms、一覧30件（結合4つ・count 付き）が 3.8ms、
  前後の id 600件が 4.5ms しかなかった。つまり `explain` を睨んでも何も出ない
  ——効くのは**往復を1本減らすこと**だけ。一覧は「購読の id を引く →
  返ってきてから記事を引く」の直列2往復で、記事を開くと前後の id で3往復めが
  乗っていた。`list_articles()`（0042）に畳んで1往復にしてある。

- **PGroonga の `&@` を、絞り込みと同じ `where` に並べて書かないこと。**
  索引が使われる計画にならない。`&@` を他の条件と一緒に置くと、計画は
  「新しい順に走りながら1行ずつ照合して、60件たまったら止まる」に化けて、
  索引を素通りして本文を読み直す——**実測 215ms**。0040 で `ilike` をやめた
  理由（Bitmap Heap Scan の recheck が本文を読み直す）と同じ形が、書き方を
  変えただけで戻ってくる。**当たる id を先に別の集合として集めること**
  （`with matched as materialized (…)`）。それだけで **11ms**。
  語が無いときは `coalesce(p_term,'') <> ''` が定数の偽になるので、
  この枝は計画に One-Time Filter だけ残って走らない。

- **真偽の引数を、索引が効くはずの条件と同じ枝に混ぜない。**
  `(p_deep and a.content_text &@ p_term)` と書くと、`p_deep` の値は計画を
  立てる時点では分からないため、**索引を使う計画そのものが立てられない**
  ——全行を舐めて1行ずつ本文を照合する形になる（実測 256ms。同じ関数でも
  「見出しだけ」なら 19ms なので、遅いのは本文の枝そのもの）。`union` で
  枝を分ければ `p_deep` は行に依らない条件になり、偽なら枝ごと実行されず、
  真なら索引がそのまま効く（**3ms**）。
  **手元で `$1` を渡して計ると速く見える**ので注意——引数に実際の値が
  入った状態で計画されるため、関数として呼んだときと計画が変わる。
  関数は関数として（`select 関数名(…)`）計ること。

- **速さを、生きた Cookie でだけ測っていた（朝いちばんを一度も測っていない）。**
  `perf-probe.mjs` はその場で新しいセッションを作ってから叩く。だから
  アクセストークンはいつも生きていて、**`/` は必ず 200 を返す**。ところが
  オーナーが実際に開くのは一晩あけた朝で、アクセストークンの寿命は1時間しか
  ない。本物の朝は必ずこうなる:

      /  → 307 /auth/refresh  → 307 /  → 200

  しかも3本とも関数が冷えている（夜のあいだ誰も叩いていない）。本番の実測:

  | 状態 | 合計 |
  |---|---:|
  | 冷えている＋トークン切れ（**本物の朝**） | **2215ms** |
  | 温まっている＋トークン切れ | 400ms |
  | 温まっている＋トークンも生きている | 200ms |

  内訳は `/` が 393ms（307 を返すだけ）、`/auth/refresh` が 848ms、
  本体が 973ms。**待ち時間の8割はコールドスタート**で、13周ぶんの計測を
  重ねても一度も見えていなかった——生きた Cookie で測る限り、この経路には
  入らないため。**「押したときの速さ」と「開いたときの速さ」は別物**として
  測ること（`scripts/morning-probe.mjs`）。

- **コールドスタートは、こちらのコードを削っても減らない。** 上の 2215ms を
  見て、まずページの依存を疑った。`/` の関数に入るファイルを Node File Trace
  （`.next/server/app/page.js.nft.json`）で数えると 134ファイル・3.4MB だが、
  **重いサーバー専用の依存は1つも入っていない**（unpdf・linkedom・rss-parser・
  @google/genai・lamejs・web-push・simplewebauthn がいずれも 0KB。いちばん
  大きいのは Next 自身のランタイム 678KB）。削るものが無いので、
  **冷やさない**ほうで直すしかない（`supabase/scheduler.sql` の
  `rsstube-warm`）。

- **「温めた直後」を「5分後」の代わりに使わないこと。** 冷め方は実測した:

  | 前の1回からの間隔 | TTFB |
  |---|---:|
  | 直後（温めた1回そのもの） | 93ms |
  | 5分 | 554ms |
  | 10分 | 1150ms |
  | 15分 | 973ms |

  **5分あけた時点でもう温かくはない。** それでも入れる価値はあって、
  冷え切った 2215ms に対して 5分毎なら 554ms——4分の1になる。間隔を詰めれば
  もう少し縮むが、そのぶんの起動を毎日払うことになるので5分で止めてある。
  **「温めてあるから速い」と書かないこと**——間隔をあけてから測ること。

- **Edge ランタイムに逃がさないこと（Next 16.3 で非推奨）。**
  朝の3本のうち `/auth/refresh` が 848ms かかるので、コールドスタートの軽い
  Edge へ移したくなる。`node_modules/next/dist/docs/.../route-segment-config/runtime.md`
  に **`'edge'` (deprecated)**、「Remove the `runtime` export from your route files」と
  書いてある。訓練データのころは推奨だったので、ここは必ず手元の docs を見ること。

- **温めを入れたあと、もう一度冷えたところから測ること（5分毎では足りなかった）。**
  `rsstube-warm` を5分毎で入れた翌日に測り直したら、**まだ冷えていた**——
  Cookie を読んで 307 を返すだけの `/` に **TTFB 1071ms**、朝の3本立てで
  合計 **3259ms**。直前の温めは4分前で、pg_cron の記録は succeeded。
  つまり**温めが動いていても、5分の隙間があれば Vercel はインスタンスを落とす**。
  同じ経路の2回目は 951ms、トークンが生きていれば 251ms なので、
  依然として待ち時間のほとんどはコールドスタートだった。
  冷め方は1分刻みでも測った（pg_cron の5分毎が割り込まない位置に揃えて）:

  | 前の1回からの間隔 | TTFB |
  |---|---:|
  | 1分 | 96ms |
  | 2分 | 263ms |
  | 3分 | 553ms |
  | 5分 | 554ms |

  **2分でもう倍**になる。温かいままにしたいなら1分毎しかない。
  **終日1分毎にはしないこと**——呼び出し回数がそのまま増える。
  実際に開く時間帯（日本時間 5:00〜8:59 = UTC 20〜23時）だけ1分毎にして、
  残りは5分毎のままにしてある（`supabase/scheduler.sql` の
  `rsstube-warm-morning`）。

- **通知から入る朝は、`/exports` が冷えている。** 温めていたのは `/` と
  `/auth/refresh` だけだったが、**ダイジェスト完成の通知をタップして開くのは
  `/exports`**（`src/app/api/cron/digest/route.ts` の `url: '/exports'`）。
  Vercel はルートごとに別の関数なので、`/` をいくら温めても `/exports` には
  届かない。**温める先は「朝いちばんに通る URL」から数えること**——
  ホーム画面のアイコンから開く道と、通知から開く道は別物。

- **温めるときは Cookie を付けて叩くこと（`/auth/refresh` を除く）。**
  未ログインで叩くと guard が Cookie を見て 307 を返して終わりなので、
  **関数は起きても、DB へ向かう道（supabase-js の初期化・PostgREST への
  TLS・問い合わせの JIT）は冷えたまま**になる。実測でも、`/` を匿名で
  起こした直後にログイン済みで叩くと 663ms、その次が 305ms と倍以上違った。
  同じ朝の3本立てでも、`/` を1本目で叩いたのに3本目の本体が 1768ms
  かかっている（TTFB は 324ms なので、遅いのは中身のほう）。
  ページのルートは Cookie を書かない（Server Component からは書けない）ので、
  付けて叩いても壊れるものは無い。
  **`/auth/refresh` にだけは付けないこと。** あそこは更新トークンを回転させて
  Set-Cookie で返す1本道で、応答を捨てると**新しい更新トークンごと捨てる**
  ことになる（セッションが死ぬ。`lib/auth/guard.ts` の注記）。
  起こすだけなら未ログインの 307 で足りる。

- **「これから開く」と分かる合図が1つだけある——朝の通知。**
  pg_cron の温めは時間帯を決め打ちで叩くので、通知が届いた瞬間には手が
  届かない。サービスワーカーの `push` ハンドラで `/` と `/exports` を
  叩いておけば、タップした先が確実に温まっている（`public/sw.js` の `wake()`）。
  **通知を出すほうを止めないこと**——`event.waitUntil` に並べて、
  温めが失敗しても通知は出るようにする。

- **朝いちばんに落ちてくる HTML の大きさは、記事の当たり外れで5倍変わる。**
  同じ `/`（未読の一覧）を同じ日に測って **66KB と 369KB**。差は
  **先頭記事の本文**で、一覧の裏で本文ペインに流している（`page.tsx` の
  `previewId`。本文がまだ抽出されていない記事が先頭のときだけ小さい）。
  実測の内訳は 191,696字のうち本文と要約の塊がおよそ6万字——**3分の1**。
  しかも**スマホでは本文ペインが `hidden md:flex` で見えていない**。
  往復は `<Suspense>` に逃がしてあるが、**運ぶ量は逃げていない**。
  手を付ける前に、このファイルの「運ぶ量を半分にしても、速くならないことが
  ある」を読むこと——机の上では見えない差なので、**回線を細くして測る**。
  手を付けるなら、**サーバーには画面の幅が分からない**ところから始めること。
  UA で振り分けると、タブレットの三ペインと細い窓のデスクトップが崩れる。

- **温めた時間帯しか測っていなかった（朝は速く、昼は3秒）。** 朝だけ1分毎に
  温める形にしたあと、オーナーが**昼にスマホから開いたら3秒以上**かかった。
  日中は5分毎のままで、しかも1分刻みで測った冷め方は **3分でもう5分と同じ**
  （1分 96ms / 2分 263ms / 3分 553ms / 5分 554ms）。「日中は使っている本人の
  操作が温め続けるので要らない」と書いていたが、**開く瞬間は、いつも使って
  いない**——直前の数時間は誰も触っていないから開くのであって、温かいのは
  「使っているあいだ」だけだった。**温める時間帯を、測った時間帯から決めない
  こと。** いまは日中2分毎、朝（UTC 20-23）だけ1分毎。

- **navigationPreload に対応していない唯一のブラウザが iPhone。**
  `public/sw.js` は「fetch ハンドラを1つでも持っていると、起動が
  『ワーカーを起こす → fetch()』の順になる」問題を navigationPreload で
  塞いだことになっているが、**WebKit は未対応**（bug 182466。Chrome と
  Firefox だけ）。つまり**手当てが効かないのが、まさに直したかった端末**。
  iPhone では今もワーカーの起動ぶんを丸ごと払ってから通信が始まる。
  ここを読んで「起動の遅さは対処済み」と思わないこと——iPhone の起動を
  速くする手は**サーバー側**（往復の本数を減らす・関数を冷やさない）にしかない。

- **リダイレクトの2本は、温まっていても 300ms 取る。** トークンが切れた朝の
  `/` →(307)→ `/auth/refresh` →(307)→ `/` を、実際のブラウザ（Chromium、
  CPU 4倍遅く・待ち時間 70ms）で `PerformanceNavigationTiming` から分解した:

  | | トークン生存 | トークン切れ |
  |---|---:|---:|
  | リダイレクト | 0ms | **303ms** |
  | responseStart | 100ms | 404ms |
  | first-paint | 168ms | 472ms |
  | load | 320ms | 647ms |

  **倍になっているのは全部リダイレクトのぶん**で、ページの組み立ても
  hydration も同じ時間しかかかっていない（responseEnd から load まで
  どちらも約 160ms）。しかも**冷えているときはここが3倍効く**——Vercel は
  ルートごとに別の関数なので、3本立てはコールドスタート3回である。
  **速さを1本の応答だけで測らないこと。**

- **JS を削っても、この3秒は減らない。** `/` が積む JS+CSS は 12本・
  展開後 670KB（brotli で約 200KB）だが、内訳は react-dom 224KB /
  Next のルーター 155KB / アプリのコード 110KB で、**大きいのは器のほう**。
  上の表のとおり responseEnd から load までは 160ms しかない（CPU 4倍遅く）。
  遅いのは運ぶものではなく、**運び始めるまで**。

- **手元の WebKit は Windows では起動しない（`libsharpyuv.dll` が無い）。**
  「iPhone の不具合は WebKit で見ること」と書いてあるが、
  `playwright install webkit --force` まで試して駄目だった。Chromium で
  測れるもの（往復・ペイロード・hydration）と、Chromium では測れないもの
  （サービスワーカーの起動、navigationPreload の有無）を**分けて書くこと**。
  後者は実機でしか出ない。

- **`workerStart` は WebKit が埋めてくれないので、ワーカー自身に時刻を聞く。**
  サーバー側を 3029ms → 246ms にしても iPhone SE では体感3秒のままだった。
  残りはサービスワーカーの起動・PWA の起動・ハイドレーションで、**どれも
  実機でしか出ない**（手元の WebKit は Windows では起動しない）。
  `PerformanceNavigationTiming.workerStart` を読めば済む話だが、Safari は
  ここを 0 のままにする。そこで `public/sw.js` の**最上位**で `Date.now()` を
  控え（＝ワーカーが起きた時刻）、画面遷移の取得を始めるときにもう一度控えて、
  ページから `postMessage` で聞く。ページ側で `performance.timeOrigin` を
  引けば、同じものさしに乗る（`src/lib/boot.ts`・`components/BootTiming.tsx`）。
  **ワーカー側で引き算しないこと**——あちらの `performance.now()` は
  ワーカーが起きた時刻が原点なので、ページとは原点が違う。
  **「起きた時刻」も一緒に返すこと。** 通信を始めるまでが 0ms でも、
  ワーカーが**前から起きていた**なら起動ぶんを払っていない——朝いちばんとは
  別の状態を見ていることになる（`bootedForThisNavigation()`）。

- **実機の数字は、サーバーへ送らずに端末へ置く。** 1人しか使っていないので、
  そのために口を1つ増やす必要が無い。localStorage に最新12件を積んで、
  設定画面のいちばん下で読む（`components/BootTimings.tsx`）。
  **読むのは `useEffect` + `setState` ではなく `useSyncExternalStore`**
  ——lint の `react-hooks/set-state-in-effect` に当たるうえ、サーバー用の
  値を別に返せるので hydration が食い違わない。

- **測る係はページではなく layout に置く。** 起動の内訳を記録する
  `components/BootTiming.tsx` を `/` のページに置いたら、**1件も残らなかった**
  ——一覧が出た瞬間に設定を開かれると、記録する前に unmount する。
  `PerformanceNavigationTiming` は「最初の1枚を読み込んだとき」の1回しか無く、
  画面を移っても増えないので、**layout に置けば遷移で作り直されず、
  どの入口から開いても必ず1件残る**。ついでに待ち時間も 2.5秒 → 400ms に
  縮めた（`performance` を読んで文字にするだけで数msしかかからない）。
  **`pagehide` と `visibilitychange` でも書き出すこと**——iOS はホームに
  戻した時点でページを凍らせるので、待っている `setTimeout` は二度と起きない。
